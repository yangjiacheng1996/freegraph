# Feature Specification: B11F1 · `Send`：动态 fan-out / map-reduce

**Feature Branch**: `b11f1-send-fanout`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "B11F1 · `Send`：动态 fan-out / map-reduce —— 交付 `Send` 原语的**运行期语义**：条件边（或节点）可以返回一个 `Send` 列表，每个 `Send` 指定「调用哪个节点」与「**用自定义入参**调用它」——从而实现 map-reduce 模式：同一个目标节点被并发调用多次，每次拿到不同的输入。本 feature 的判定是：**map-reduce 模式可运行**。"

- **Q3**：当 `Send` 指向一个不存在的节点时，报错信息里应该写些什么？
  → **A：同时点名「产生者节点」与「目标节点」**（如：节点 `'fan'` 的 `Send` 指向了不存在的节点 `'nope'`）
  —— 定位最快。
  ⇒ **上游自查（收窄纪律）**：上游在该场景**只 warning + 忽略**（`pregel/_algo.py:978`）⇒
  **没有失败消息可抄** ⇒ 落在**必须自研区 ③**（上游没有的能力）⇒ ⇒ 消息内容属 freegraph 自研
  ⇒ 请发起者拍板 ⇒ 拍板结果 = **A**。
  ⇒ 落点：**FR-007**（消息 MUST **同时**点名两处）· **裁定 7** · SC-003 · Edge Cases。
- **Q4**（**分析轮补问** · 2026-11-14）：同一个目标节点在同一轮里**既被静态边触发**、**又被 `Send`
  派发**时，这两种调用的写入**谁先归约**？
  → **A：标准触发在前**（标准触发任务没有产生者 ⇒ 它**排在所有 fan-out 调用之前** ——
  **上游 PULL 路径先于 PUSH 路径**）—— 按**推荐项**落定（**经发起者授权**：「授权按推荐项修复上述问题」）
  ⇒ ⇒ **回写进 spec 的 FR-005**（该口径**用户可见** ⇒ MUST 住在 spec 层而非只活在 plan 层）。
  ⇒ **上游自查（2026-11-14 复核更正）**：上游 `apply_writes` 按任务路径排序 ⇒ **PULL（标准触发）
  路径先于 PUSH（fan-out）路径** ⇒ **所有标准触发任务先于所有 fan-out 任务**（不只是同一目标内）
  ⇒ ⇒ 与 Q4 的推荐项**同向且更强** ⇒ **照抄上游**（原则 XI ①），**不是**自研区 ②。
  ⇒ 落点：**FR-005** · **裁定 6** · **P-13** · SC-008 / SC-009 · plan **D-01** · data-model §3.3。
  ⚠️ **本轮**除 Q4 外未新增其它提问 ⇒ 澄清轮第 1 次的 **Q1–Q3**（入参形态 / 目标不存在 / 混合调度）
  **全部保持**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 同一个节点被多次调用，每次拿到不同的任务（Priority: P1）

作为用户，我有一个 `worker` 节点要处理 2 个不同的任务，我希望它**被调用两次**，
每次拿到**自己的**任务参数（而不是「同一份状态跑两遍」）。

**Why this priority**: 这是本 feature 的**全部存在理由**（立项书 §5.2 B11F1 行的小目标逐字：
「map-reduce 模式可运行」）—— 没有它，`Send` 只是一个数据类型。

**Independent Test**: 一个节点返回 `[Send("worker", {"n": 1}), Send("worker", {"n": 2})]`
⇒ 断言 ① `worker` 的副作用计数 == **2**；② 两次收到的入参**分别逐字等于** `{"n": 1}` 与 `{"n": 2}`。

**Acceptance Scenarios**:

1. **Given** 一个节点返回两个指向同一目标的 `Send`（各自的 arg 不同），
   **When** 执行该图，**Then** 目标节点**被调用两次**，两次的入参**分别逐字等于**各自的 arg。
2. **Given** 一个节点返回两个指向**不同**目标的 `Send`，
   **When** 执行该图，**Then** 两个目标**各被调用一次**，各自拿到自己的 arg。
3. **Given** 一个节点返回**单个** `Send`（非列表），
   **When** 执行该图，**Then** 目标节点**被调用一次**（与返回单元素列表**同款**）。

### User Story 2 - fan-out 的产出按归约器汇合（Priority: P2）

作为用户，多个 worker 的产出应当**按归约器汇合到同一状态 key**，
从而得到汇总结果 —— 而且汇合的**顺序是确定的**（同一份图跑两次，结果必须逐项相等）。

**Why this priority**: 提示词 **§5 SC-002** 与 **§6 A2** 的逐字要求；且「顺序不确定」会让
map-reduce 的结果**不可复现** ⇒ 下游 freechain 无法对结果做断言。

**Independent Test**: 两个 worker 各写一条消息到同一个**归约型**通道 ⇒ 断言最终值
== 两次产出的**归约结果**；同一份规格重复跑 **≥ 3** 次 ⇒ 结果**逐项相等**。

**Acceptance Scenarios**:

1. **Given** 两个 `Send` 指向同一目标、目标各写一条消息到同一归约型通道，
   **When** 执行该图，**Then** 汇合通道的最终值 == 两次产出的归约结果（**顺序确定**）。
2. **Given** 同一份图规格，**When** 重复执行 **≥ 3** 次，**Then** 最终状态与执行序列**逐项相等**。

---

### User Story 3 - `Send` 的目标写错了要立刻报错（Priority: P3）

作为用户，如果我把 `Send` 的目标节点名**写错了**，我希望**立刻得到明确的报错**，
而不是「这次 fan-out 被悄悄丢掉、结果少了一半」。

**Why this priority**: 上游对「`Send` 目标不存在」是 **warning + 忽略**
（实测：`Ignoring unknown node name nope in pending sends`）⇒ freegraph 的红线是
「**显式失败优于静默**」⇒ 这条故事把上游的静默改成**可判定**。

**Independent Test**: 让一个节点返回 `Send("no-such-node", {...})` ⇒ 断言**显式失败**，
且异常消息**点名** `"no-such-node"`。

**Acceptance Scenarios**:

1. **Given** 一个节点返回 `Send("no-such-node", {...})`，**When** 执行该图，
   **Then** 系统**显式失败**，异常消息**点名**该目标节点名，**MUST NOT** 静默丢弃该 `Send`。
2. **Given** 一个节点返回 `Send(Command.PARENT, {...})`（目标 = 保留名），
   **When** 执行该图，**Then** 系统**显式失败**（`NotImplementedError` · 点名 `__parent__`
   与「子图属 v2 能力」）⇒ 与「名字写错了」（`ValueError`）**可区分**。

### User Story 4 - 没有 `Send` 时行为一字不变（Priority: P4）

作为用户，普通静态边的执行行为 MUST 与引入 `Send` 之前**完全一致** —— 我已有的图不该被影响。

**Why this priority**: 提示词 **§3 P3** / **§5 SC-003** 的逐字要求；且 `Send` 是「**新增**的
返回形态」⇒ 若它污染了既有路径，既有断言会偶发红。

**Independent Test**: 静态边用例**全量回归**（既有测试套件零改动通过）⇒ 断言通过率 == **100%**。

**Acceptance Scenarios**:

1. **Given** 一张只用静态边的图，**When** 执行该图，
   **Then** 行为与引入 `Send` 之前**逐项一致**（既有断言一条不删、零改动通过）。
2. **Given** 一个节点返回普通 `dict`（非 `Send`），**When** 执行该图，
   **Then** 其写入路径与归约行为**一字不变**。

### User Story 5 - fan-out 与普通边混在一张图里也能判清（Priority: P5）

作为用户，一张图里可能**既有**静态边触发、**又有** `Send` 任务；
我希望「谁被调用了几次、每次拿到什么」**说得清**，而不是含糊。

**Why this priority**: 提示词 **FR-006** 逐字要求「明确『普通边与 `Send` 混合』时的调度语义
⇒ 并在 spec 中写死」；且这是最容易实现走偏的一处（叠加 vs 取代）。

**Independent Test**: 同一节点既有静态边（指向**另一个**目标）、又返回指向第三个目标的 `Send`
⇒ 断言 ① 两个目标**都被调用**；② 同一个目标**不会**既被标准入参调用、又被 `Send` 调用。

**Acceptance Scenarios**:

1. **Given** 节点 X 既有静态边 X→Y、又返回 `Send("Z", ...)`，
   **When** 执行该图，**Then** **Y 与 Z 都被调用**（叠加）。
2. **Given** 节点 X 既有静态边 X→Z、又返回 `Send("Z", ...)`，
   **When** 执行该图，**Then** **Z 只被 `Send` 调用**（标准入参的那次**不发生**）
   ⇒ 总调用次数 == `Send` 的条数。

### User Story 6 - 一次返回里既派发又写入（Priority: P6）

作为用户，我希望派发任务的那个节点在**同一次返回**里**顺便写一点状态**
（比如记录「本次派发了 3 个任务」），而不是被迫拆成两个节点。

**Why this priority**: 上游 1.2.11 的 `Command` 允许 `goto` 与 `update` **同时**生效
（实测 **E-08**）⇒ 澄清轮第 2 次（发起者拍板 **B**）要求**照抄上游** ⇒ 缺了它，
freegraph 的 map-reduce 写法与上游**能力不对等**（用户在 freechain 里照搬上游写法会撞墙）。

**Independent Test**: 一个节点返回
`Command(goto=[Send("worker", {"n": 1}), Send("worker", {"n": 2})], update={"messages": ["from-fan"]})`
⇒ 断言 ① 最终状态**含** `"from-fan"`；② `worker` **被调用两次**（各自入参正确）⇒ **两条断言同时成立**。

**Acceptance Scenarios**:

1. **Given** 一个节点返回「`goto` 里放两个 `Send` + `update` 写一条消息」，
   **When** 执行该图，**Then** 该消息出现在最终状态里，**且** `worker` 被调用两次
   （两条断言**同时**成立 —— 写入不吞派发、派发不吞写入）。
2. **Given** 一个节点返回 `Command(goto="worker")`（纯跳转 · **不含** `Send`），
   **When** 执行该图，**Then** 行为与引入 `Send` 之前**逐字一致**
   （既有 `goto` 语义**不受影响** · B9F1 的回归不破）。

### Edge Cases

- **节点返回 `Send`（单个）** ⇒ 产生 **1** 个 fan-out 任务（与单元素列表**同款**）。
- **节点返回 `list[Send]` / `tuple[Send, ...]`** ⇒ 产生 **N** 个 fan-out 任务（**保序**）。
- **节点返回空列表 `[]`** ⇒ **显式失败**（内置 `TypeError` · 与 B9F1 的 **V-9** 同款
  ⇒ 空列表的语义**无歧义**：不可能既「空命令列表」又「空 fan-out 载荷」）。
- **节点返回混合列表**（`Send` 与 `dict` / `Command` 混装）⇒ **显式失败**（内置 `TypeError`）。
- **命令列表里混入 `Send`**（`[Send(...), Command(...)]`）⇒ **显式失败**（内置 `TypeError` ·
  B9F1 **V-10** 同族）⇒ 「命令列表」与「fan-out 载荷」**两种列表语义不得混谈**。
- **`Command(goto=Send(...))` / `Command(goto=[Send(...)])`** ⇒ **支持**（上游同款 · 澄清轮第 2 次
  Q1 拍板 **B**）⇒ `goto` 槽位里的每个 `Send` 各自成为**一个 fan-out 任务**（下一轮 · arg 逐字）。
  ⚠️ **`goto` 槽位可**混装**节点名与 `Send`**（`Command(goto=["a", Send("b", {...})])`）
  ⇒ **上游同款**（上游 `graph/state.py:1768-1774` 逐个元素分派：节点名 → 分支写 · `Send` → `TASKS` 写）
  ⇒ **MUST NOT** 把整个序列当同一种东西处理。
  ⚠️ **`Command(goto=Send(...), update={...})`** ⇒ **派发与写入同时生效**（上游同款 · 实测 **E-08**）
  ⇒ 写入归**产生节点**名下（B9F1 裁定 16）· 派发任务在**下一轮**执行。
- **`Command.goto` 里出现非法元素**（非 `str` / 非 `Send`）⇒ **显式失败**（内置 `TypeError` ·
  B9F1 **V-12** 同族）。
- **`Send` 的 `node` 不是 `str`** ⇒ **显式失败**（内置 `TypeError`）。
- **失败消息的形态** ⇒ 目标不存在时 MUST **同时点名产生者节点与目标节点**
  （澄清轮第 2 次 Q3 拍板 **A**）⇒ 其余 `Send` 相关的失败（保留名 / 哨兵 / 形态非法）
  MUST **点名出错的槽位与取值**（原则 VIII 术语纪律）。
- **`Send` 的 `node` 是空串** ⇒ **显式失败**（内置 `ValueError`）。
- **`Send` 的 `node` 是 `Command.PARENT`（`"__parent__"`）** ⇒ **显式失败**
  （`NotImplementedError` · 点名 `__parent__` 与「子图属 v2 能力」· 与 B9F1 裁定 7 **同款**）。
- **`Send` 的 `node` 是 `START`（`"__start__"`）/ `END`（`"__end__"`）** ⇒ **显式失败**
  （内置 `ValueError` · 两者**都不是**可被调用的节点）。
- **`Send` 的 `arg` 是任意对象（含 `None`）** ⇒ **不校验**（**逐字**传给目标节点）⇒
  目标节点**自己**负责解释。
- **fan-out 目标节点**在下一轮**同时**被别的节点静态触发 ⇒ **叠加**（标准入参那一次**照常发生**）。
- **fan-out 目标节点**就是**产生者自己**（自投）⇒ 允许（下一轮以 arg 再跑一次）⇒
  由 `run_super_steps` 的 **`max_steps`** 兜底（**公开 `recursion_limit` 归 B13F1**；本 feature 的用例 MUST 显式传小 `max_steps` 或构造终止图，MUST NOT 依赖「无限跑」）。
- **同一份载荷里 `Send` 重复指向同一目标、arg 相同** ⇒ **N 次独立调用**（**MUST NOT** 去重）。
- **fan-out 轮里某个调用抛异常** ⇒ 异常**原对象**向上抛出 · **整轮不合并**（B7F1 的整轮原子性）。
- **fan-out 轮里某个调用中断** ⇒ 中断按 **B12F1** 的口径**收集并合并抛出**；⚠️ **同一节点被 N 次调用**时，
  每次调用的**任务级现场 MUST 相互独立**（中断 id / 恢复值**不串扰** · `DR-01` · T027/T034）。
- **产生 `Send` 的节点本轮还有其它写入** ⇒ **载体 A（`Command.goto=Send(...)` + `update=`）支持**
  （上游同款 · 实测 **E-08** · 澄清轮第 2 次 Q1 拍板 **B**）；**载体 B（节点直接返回 `list[Send]`）**
  **不支持**（一个返回值只能是一种形态）⇒ 需要「既 fan-out 又写状态」的用户**MUST** 用载体 A
  （`Command(goto=[Send(...), ...], update={...})`）或拆成两个节点。
- **同一节点在**同一轮**内既被 `Command.goto` 装 `Send` 派发、又有静态边指向同一目标**
  ⇒ **叠加**（上游同款 · 实测 **E-02** · 目标被调用 **2** 次：一次标准入参 · 一次自定义）
  ⇒ 与**载体 B** 的口径**不同**（载体 B 是「`Send` 胜出」）⇒ 详见 **裁定 5** 的**按载体分列表**。
- **上一轮产生过 `Send`、本轮不再产生** ⇒ 旧的 fan-out **不残留**（下一轮不再有那些任务）。
- **fan-out 目标同时是「多源屏障组（B7F4）」的目标** ⇒ **屏障组不抑制**（屏障语义优先）⇒
  该目标的标准入参那次**照常发生**（**MUST NOT** 因 `Send` 拆掉屏障）⇒ 见 FR-006 / SC-005 的例外。
- **上游缺席**（差分场景）⇒ 差分用例 **skip**（沿用 B5F2 的「缺席即 skip」纪律）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001（fan-out 的载体 = **双载体** · 澄清轮第 2 次 Q1 拍板 B）**：系统 MUST 支持**两种**载体，
  二者**共用同一套** fan-out 语义（落点 · 入参形态 · 次数 · 失败信号 · 并发）：
  ⚠️ **载体 A（上游同款）**：`Command(goto=Send(...))` / `Command(goto=[Send(...), ...])` ⇒
  `goto` 槽位里的每个 `Send` 各自成为**一个 fan-out 任务**；`goto` 槽位**可**与**节点名混装**
  （`Command(goto=["a", Send("b", {...})])` ⇒ 节点名 → 分支写 · `Send` → fan-out 任务 ·
  **上游同款** · `langgraph/graph/state.py:1768-1774` 逐个元素分派）⇒ **MUST NOT** 把整个序列
  当同一种东西处理；`Command(goto=Send(...), update={...})` ⇒ **派发与写入同时生效**（上游同款 ·
  实测 **E-08**）；
  ⚠️ **载体 B（验收脚本锁定）**：节点函数 **直接返回** `Send` 或 `list[Send]` / `tuple[Send, ...]`
  ⇒ 每个 `Send` 产生**一个独立的 fan-out 任务**；**载体 B 不承载写入**（一个返回值只能是一种形态）。
  ⚠️ **条件边形态的运行期语义归 B8F1**（`GraphSpec.conditional_edges` **恒空** · B7F1 的 **V-8**
  ⇒ 本 feature **MUST NOT** 实现条件边路由）⇒ 本 feature **接线**（下游承接 **D-1** / **D-6**）·
  **MUST NOT** 越界实现。
  ⚠️ **本 feature 的 SC 不覆盖「条件边返回 `Send`」这一半**（SC-001…SC-022 只覆盖**载体 A** +
  **节点返回的载体 B**）⇒ 条件边那一半由 **B8F1** 的独立判据判定
  （**避免把未交付项算进本 feature 的覆盖率** · 宪法原则 VI）。
  ⚠️ **两种列表语义不得混谈**：载体 B 的载荷元素 MUST **全部**是 `Send`；混入 `dict` / `Command`
  ⇒ 内置 **`TypeError`**；命令列表（B9F1）里混入 `Send` ⇒ 内置 **`TypeError`**（B9F1 **V-10** 同族）。
  ⚠️ **空列表 `[]`** ⇒ 内置 **`TypeError`**（与 B9F1 的 **V-9** 同款 ⇒ 空列表**无歧义**）。
  ⚠️ **`goto` 槽位里的非法元素**（非 `str` / 非 `Send`）⇒ 内置 **`TypeError`**（B9F1 **V-12** 同族）。

- **FR-002（`Send` 的落点 = 与静态边 / `goto` 同族的**下一轮任务** · 承接 H-1 / H-2）**：fan-out 任务 MUST
  与静态边 / `goto` **同为下一轮任务** ⇒ MUST **NOT** 另造第三类触发源标识、**NOT** 另造第三种跳转语义。
  ⚠️ **口径澄清（2026-11-14 · 修复分析轮 M1）**：fan-out 任务是「**派发任务**」⇒ **不占用 / 不消费**
  任何**边触发源版本**（它是「派发」不是「触发」）⇒ ⇒ 因此它**不是**第三类触发源；「同族」指的是
  **落点（下一轮）与触发判定之外的任务构造路径**，**不是**「必须登记为 `("e", 源节点名)` 边触发源」。
  ⚠️ **落地口径**：产生 `Send` 的节点 X 在**本轮**执行 ⇒ 其 fan-out 任务在**下一轮**执行
  （**不在本轮内执行** · 上游同款：SEND tasks 在 superstep n+1）⇒ 与 `goto`（B9F1 裁定 1）**同族**。
  ⚠️ **生命周期（一次性载荷 · 上游同款）**：fan-out 载荷在**下一轮被消费后 MUST 清空**
  （上游 `TASKS` 通道 = `Topic(Send, accumulate=False)` · `pregel/main.py:809` ⇒ 每步清空）
  ⇒ **MUST NOT** 在再下一轮重复触发；X **再次执行** ⇒ 以**新载荷替换**（含空集 ⇒ 旧的被清空）
  ⇒ MUST NOT 留下「幽灵 fan-out」。
  ⚠️ **fan-out 任务 MUST NOT 触发「有值」门槛**（与静态边**同款** · B9F1 裁定 17）
  ⇒ 目标节点**照跑**（哪怕它订阅的通道都没值）。

- **FR-003（入参形态 = 自定义 arg **逐字替代**标准入参 · 提示词 §10 风险项 · **写死**）**：
  fan-out 任务的入参 MUST **逐字等于**该 `Send` 的 `arg` ⇒ MUST **NOT** 与图状态合并、
  MUST **NOT** 经稀疏读过滤、**MUST NOT** 按目标节点的订阅集裁剪。
  ⚠️ **上游同款**（实测 **E-03 / E-04**：目标节点只看到 arg 的 key）。
  ⚠️ **与 C4 的关系**：C4 管的是「**从通道读**」；fan-out 的 arg 是**外部给定**的入参 ⇒
  **不经过**稀疏读路径 ⇒ **不是** C4 的例外，而是 C4 的**适用范围之外**。
  ⚠️ **与 C8 的关系**：fan-out 任务**不读**通道 ⇒ **fresh 读**对它**无意义**。
  ⚠️ **与 C5 / `NodeFunc` 入参注解的关系（2026-11-14 · 修复分析轮 H3）**：**C5** 的
  「`f(state: dict) -> dict`」与 **`NodeFunc.__call__(state: StateDict)`** 的**稀疏 dict 入参**
  只适用于**标准触发 / `goto`** 调用；经 `Send` 调用的目标节点入参 MUST 是 **`arg` 原样**
  （可为非 `dict` / `None` · 上游实测 **E-10**）⇒ ⇒ `NodeFunc` 的 docstring / C5 的**契约注记**
  MUST 显式写明这一例外（**不改 `Send` 的字段 / 构造 / 校验** · 见 **F-11**）。

- **FR-004（多次调用 = N 次独立调用）**：载荷里的 **N** 个 `Send` MUST 产生 **N** 次**独立**调用
  ⇒ 指向**同一**目标的多个 `Send` MUST **各自**调用一次（**MUST NOT** 去重）。
  ⚠️ **N 次调用 MUST 是 N 个独立任务**（各自的入参、各自的写入、各自的成功 / 失败）
  ⇒ 某一个失败**不**影响其它 N−1 次的**入参**（但**整轮不合并** · FR-011）。

- **FR-005（写入路径 = 共用同一条合并路径 · 承接 H-2）**：fan-out 调用产生的写入 MUST 与普通节点调用
  **共用同一条状态写入合并路径**（**C6**）：逐 key 应用该通道的归约器 · 无归约器则**覆盖** ·
  **未知 key ⇒ `InvalidUpdateError`**（**C6** · L1 已冻结）· **覆盖型通道同轮多写 ⇒ 显式失败**
  ⇒ MUST **NOT** 为 fan-out 另写一条合并实现。
  ⚠️ **归属**：fan-out 调用的写入 MUST 归到**目标节点名**名下（`node_writes` 的**按节点分组**）
  ⇒ 与普通调用**同款** ⇒ B8F1 的 fresh 读复用前提**不被破坏**。
  ⚠️ **归并顺序（确定性 · 上游同款 · 澄清轮第 2 次 Q2 拍板 A · 分析轮补问 Q4（2026-11-14）补齐 · 2026-11-14
  复核更正 · 逐字）**：一轮内的任务顺序 MUST 为**上游任务序**：
  ① **标准触发任务**（由边触发源触发）⇒ 按**目标节点名序**（上游 PULL 路径 `(PULL, 节点名)`）；
  ② **fan-out 任务**（`Send` 派发）⇒ 在**全部标准触发任务之后**，按**产生者任务序 · 载荷内的
  `Send` 序号**（上游 PUSH 路径 `(PUSH, idx)`；`idx` 顺序 = 前一超步 `TASKS` 的写入顺序 =
  产生者任务序 + 载荷内 `Send` 序号）⇒ **MUST NOT** 以**目标节点名**为 fan-out 的首要键
  （上游不是这样）；
  ③ **MUST NOT** 让完成时刻的竞态决定顺序（提示词 §10 · B12F1 裁定 3 / 15 · 上游
  `pregel/_algo.py:253-256` 的路径排序）⇒ **MUST NOT** 按「谁先派发」跨产生者交错。
  ⚠️ **对 B7F1 / B12F1 既有「节点名序」断言的取代范围（2026-11-14 · 修复分析轮 C2 · F-14）**：
  本条的「TaskId 归并序」在**含 fan-out 任务的轮**里**取代** B7F1 契约 **I-12**（报告 / 写入顺序 =
  节点名序）与 B12F1 契约 **§6 / I-8**（合并顺序 = 节点名序）的**字面口径**；**标准触发任务之间**
  仍按节点名序（与旧断言一致）⇒ ⇒ 该取代 MUST 走 **F-14 / T-15** 的**拆分而不删**回溯修订。
  ⚠️ **口径的来历（**留白已闭合 + 事实更正**）**：初版 spec 的第二级键写作「产生**该任务**的节点名序」
  ⇒ 对**标准触发任务**（由**别的**节点经边触发）**无定义** ⇒ 该留白由 plan 的 **D-01** 冻结为「空标签 ⇒
  标准在前」⇒ **2026-11-14 分析轮发现 ⇒ 经发起者授权按推荐项落定并回写本条**（分析轮补问 **Q4** · 2026-11-14）
  ⇒ ⇒ 该口径**用户可见**（汇合结果的顺序）⇒ 故 MUST 住在 spec 层而非只活在 plan 层。
  ⚠️ **2026-11-14 复核更正**：原稿称「上游按完成时刻竞态」不成立（上游 `apply_writes` 明确按任务路径
  排序）⇒ 现口径**照抄上游**；「产生者任务序」= 产生该 `Send` 的**任务**在产生轮的 TaskId 序

- **FR-006（普通边与 `Send` 混合 ⇒ **按载体分列**）**：同一 super-step 内**既有**静态边触发、

  ⚠️ **载体 A（`Command.goto` 装 `Send`）⇒ 叠加**（**上游同款** · 实测 **E-02**）⇒ 目标被调用
  **N+1** 次（一次标准入参 · N 次自定义；单 `Send` 时 = **2** 次）⇒ 与上游**逐字一致**
  （**P-10** · 差分 **D-33** 判词 SAME）；

  ⇒ **照常**在下一轮被触发；

  ⇒ 标准入参那一次**照常发生**）。

  **用户可见** ⇒ 一并约束 **SC-005 ①**（屏障场景不受「标准入参调用 == 0」约束）。

### Key Entities

- **`Send`（fan-out 载荷）**：不可变记录（`node` / `arg` 两字段）—— **类型**在 **L1**（与 `Command` 同模块 ·
  `freegraph/contracts/types.py` · 门面再导出为 `freegraph.graph.Send`），**运行期语义**由本 feature 交付
  （`node` = 目标节点名 · `arg` = **逐字**传给目标节点的入参）。
- **fan-out 载荷**：节点（或条件边）返回的 `Send` / `list[Send]` / `tuple[Send, ...]` —— **N 个 `Send` ⇒ N 个
  fan-out 任务**（保序）；**MUST NOT** 与「命令列表」混谈。
- **fan-out 任务**：由一个 `Send` 产生的**独立**节点调用 —— 在**下一轮**执行 · 入参 = arg 逐字 ·
  写入归**目标节点名**名下 · 与普通调用**共用同一条**合并路径（C6）。
  **内部 / 持久化标识**：结果槽与次序键用 **TaskId（`int`）**；持久化 `task_id` = **节点名**（标准任务）或
  **`f"{节点名}:{TaskId}"`**（fan-out 任务 · **F-13**）⇒ 同一节点 N 个任务**各自唯一**。
- **边触发源**：使节点被触发的东西（标识 `("e", 源节点名)`）—— **静态边** · **`Command.goto`**
  （B9F1）。⚠️ **fan-out 任务不是边触发源**：它是**派发任务**（下一轮落点与 `goto` 同族 ·
  **不消费触发源版本**）⇒ **MUST NOT** 登记为 `("e", 源节点名)`（**F-14 / M1**）。
- **动态边表（`dynamic_edges`）**与**fan-out 表**：调度状态里的两处**运行期**记录 ——
  前者记「源节点最近一次执行的跳转目标」（B9F1 · 裁定 12）· 后者记「**产生者任务**最近一次执行
  产生的 fan-out 载荷」（键 = **TaskId**，同一节点在一轮内执行多次时**各次任务分别记录**；
  载荷**另带 `producer` = 产生者节点名** ⇒ 载体 B 抑制按 `(producer, target)` 匹配）⇒
  两者**同生命周期**（产生者任务**再次执行**即**整体替换**；fan-out 载荷在下一轮**消费后清空**）。
- **归约器（reducer）**：通道的合并语义 —— fan-out 的 N 次写入按**归并顺序**逐条归约（C2 / C6）。
- **归并顺序（写入合并的次序键 · 澄清轮第 2 次 Q2 拍板 A · 2026-11-14 复核更正）**：
  **上游任务序** = **（标准触发任务按目标节点名序）→（fan-out 任务按产生者任务序 · 载荷内的
  `Send` 序号）** —— **标准触发任务全部先于 fan-out 任务** ⇒ **可复现**（**MUST NOT** 由
  完成时刻的竞态决定；**MUST NOT** 以目标节点名作为 fan-out 的首要键）。
- **无效更新错误（`InvalidUpdateError`）**：**L1 契约层**冻结的**显式失败**信号 ——
  节点写入了状态 schema 中不存在的 key（**C6** · 结构化字段 `invalid_keys`）。
