**Feature Branch**: `b9f1-command-primitive`

**Created**: 2026-11-11

**Status**: Draft

## Clarifications

### Session 2026-11-11（澄清轮 · **发起者拍板**）

- **Q1**：节点既有**静态边**（固定下一站）又返回 `Command(goto=...)`（临时改道）时，两条路应该
  **都走**、还是 `goto` 把固定下一站**顶掉**？
  → A: **叠加** —— 静态边目标与 `goto` 目标**都**在下一轮被触发（与上游 LangGraph 1.2.11
  **实测同款**）。
  发起者的**概念锚点**（逐字）：「**Edge 是给框架和人看的，节点本身不知道 Edge 的存在**；
  而 `goto` 相当于 **Edge 在节点中的一个标签**，让节点能获取下一站 Edge 信息」
  ⇒ 静态边 = **框架层写死**的边 · `goto` = **节点层自己声明**的边 ⇒ **两者同类**
  ⇒ 节点**没有**「取消框架那条边」的语义 ⇒ **叠加**是自洽的（不是"顶掉"那种特批）。
  ⇒ 落点：**裁定 3**（已按此改写）· **FR-008** · SC-007 · Edge Cases（`goto` 与静态边并存）。
- **Q2**：节点声明了一条 `goto` 边、但目标**在本图里不存在**（拼错名字、或跳向 `Command.PARENT`
  这个 v1 还没有的父图）时，应该**当场报错**还是**悄悄跳过继续跑**？
  → C: **分开报错** —— 节点名不存在 ⇒ **`ValueError`**（写错了）；`Command.PARENT` ⇒
  **`NotImplementedError`**（"子图属 v2 能力"· 沿用仓库 `interrupt()` 未接线的**同款用法**：
  `src/freegraph/_primitives.py` 的 `interrupt()` 与 `StateGraph` 的方法在未接线时都抛
  `NotImplementedError` 并**点名归属的 feature**）。
  ⇒ 理由：`Command.PARENT` **不是写错了** —— 它是**合法常量**、只是**本版本还没实现子图**
  ⇒ 与「拼错名字」**语义不同** ⇒ 分开报错，用户（及下游 freechain）可分别捕获
  「还没做」与「写错了」。
  ⇒ 落点：**裁定 7**（已按此改写）· **裁定 8**（保持 `ValueError`）· **FR-005** / **FR-007** ·
  SC-005 / SC-009 · Edge Cases。
  ⚠️ **对 B7F1 不变量的刻意偏离（登记）**：B7F1 的「一个 feature 只用**两种**内置异常
  （`ValueError` / `TypeError`）」⇒ B9F1 引入**第三种**（`NotImplementedError`）⇒
  **刻意偏离 · 已登记**（理由 = 「合法常量但能力未实现」与「值写错了」是**两种**语义，
  且仓库已有 `NotImplementedError` 的既有用法）⇒ MUST NOT 被当成实现漂移。
- **Q3**：节点返回 `Command(goto=END)` 时，`END` 应该表示「这一轮之后不再往下走、整张图就此结束」，
  还是「这个槽位不产生动作、不影响别的触发源继续推进」？
  → A: **不产生动作** —— `END` 只是「**这一位没有下一站**」（**空动作**）⇒ 不影响别的触发源
  （静态边 / 条件边）照常推进；**图是否结束由「收敛」决定**（没有任何触发源了自然就停）。
  ⇒ 理由：与上游 LangGraph 1.2.11 **实测同款**（上游把 `END` 特判成「不是节点、不需要分支过去」·
  `graph/state.py:1771-1774` · 实测静态边照走）；且语义更干净 —— **终止是「收敛」的结果**，
  不是某一条 `goto` 强行掐断的结果（否则「是谁终止的」在 trace 里说不清）。
  ⇒ 落点：**裁定 5**（已按此改写）· **FR-007** · SC-008 · Edge Cases。
- **Q4**：节点能不能一次性 `goto` **多个**目标（例如 `Command(goto=["a", "b"])`，下一轮两个节点都跑）？
  → A: **支持多目标** —— 序列里的每个目标**各自**成为下一轮的一条边（上游同款 · 已实测）。
  ⇒ 理由：① L1 冻结的 `goto` 类型本来就含「目标名序列」⇒ 契约层的类型面**言而有信**；
  ② 「一条边可以有多个目标」与静态边**完全同款** ⇒ 零新概念；③ **与 B11F1 的 `Send` 不重叠** ——
  `Send` 是「带**自定义入参**地分发到某个节点」，`goto` 是「跳到某个节点、沿用它自己的入参」
  ⇒ 两者是**两件事**，不因本条而混淆。
  ⇒ 落点：**裁定 9**（已按此改写）· **FR-007** · SC-011 · Out of Scope（`Send`）。
- **Q5**：`goto` 的目标必须被**记住**（直到源节点下次执行）⇒ 这处「运行期」存储**放在哪里**？
  → A: **放调度状态对象里**（B7F1 的 `SchedulerState` **增一个带缺省值的字段**）⇒
  `SchedulerState()` 的**构造签名与名字逐字不变** ⇒ 现有调用方（**B7F2 / B7F3 / B8F1 / B12F1**）
  **零改动**。
  ⇒ 理由：① B7F1 已把「已消费版本 / 轮次计数 / 各通道版本」这些**运行期记录**统一放在调度状态里
  （那是它的既定归属 · 裁定 16 / 21）⇒ `goto` 目标**同址**才不出现第二套状态；② B（另建状态对象）
  要改 B7F1 已冻结的**入口签名** ⇒ 四个下游 feature 全要改；③ C（放进图规格）破坏「同一份规格可
  安全跑多次」的可重复性承诺；④ 只**增一个带缺省值的字段** ⇒ **不改变任何构造签名与名字**
  ⇒ B7F1 的**跨 feature 冻结面不破**。
  ⇒ 落点：**裁定 12**（已按此改写）· **FR-002** · SC-015 / SC-019 · plan 阶段的**登记项**
  （字段名由 plan **冻结**）。

### Session 2026-11-11（澄清轮 · **第 2 次** · 发起者拍板）

- **Q1**：节点能不能返回**一个命令列表**（例如 `return [Command(goto="a"), Command(update={...})]`），
  让一个节点同时发出多条命令？
  → B: **支持列表**（**上游同款**）—— 可返回 `list[Command | dict]`，多条命令按**列表顺序**依次生效；
  V-4 的返回值口径**一并放宽**。
  ⇒ **评估结论（发起者要求先评估兼容性）**：
  ① **对 `harness/demo/target.py`（MVP 验收契约 · 原则 III）零影响** —— 它**完全没用 `Command`**
  （节点一律返回普通 dict）⇒ 原则 III 冻结的 7 项同名同签名里也**不含** `Command`；
  ② **对 `harness/demo/acceptance.py` / `graph_core.py` 零影响** —— C16 只查门面**导出了** `Command`，
  用例是**单个** `Command(goto=END, update={...})`；
  ③ **对契约 C16 零影响** —— Q8 `:258` 逐字是 `Command(goto=..., update=..., resume=...)`，
  **不含**「列表返回」；
  ④ **对官方文档口径零影响** —— `harness/docs/oss/python/langgraph/use-graph-api.md:2122-2199`
  的公开用法是**返回单个 Command**；`Command[Literal["node_b", "node_c"]]` 是**类型参数**（给图渲染用），
  **不是**运行时列表 ⇒ 文档**未**把「返回命令列表」列为公开写法；
  ⇒ **真正受影响的只有一种写法**：照搬上游、节点 `return [Command(...), ...]` —— 而上游**支持**它
  （`graph/state.py:1456-1484` 的 `_get_updates` + `:1752-1758` 的 `_control_branch`）。
  ⇒ **「上游久经测试」这条在列表上成立一半**：上游**自己的高层代码**把「多个命令」**归一**成
  「一条命令 + 拼接的 goto」（`prebuilt/tool_node.py:895-910` 的
  `replace(parent_command, goto=... + output.goto)`）⇒ 上游也认为「多条命令」≡「一条命令、多目标、
  多 key 写入」⇒ 列表是**实现层的便利形态**、不是独立语义 ⇒ freegraph 支持它**不引入新语义概念**。
  ⇒ **发起者的偏好**（逐字）：「**LangGraph 上游是经过大量测试的，被证明是安全的，能与上游保持一致
  是我个人的偏好**」+「**多条命令按列表顺序依次生效，在一定程度上保持了串行，也是安全的**」
  ⇒ **判定**：与上游保持一致 ⇒ 选 **B**。
  ⇒ **成本可控**：只需**放宽** V-4 的返回值口径（`dict` / `Command` / `list[Command | dict]`）
  —— 属**协变放宽**（**接受面**变大 ⇒ 对既有调用方**零破坏** · 与**裁定 11** 同款）
  ⇒ 唯一**新写死**的口径 = 「多条命令写同一个 key ⇒ 按**列表顺序**合并」（串行 ⇒ 与上游
  `_get_updates` 的 `updates.extend(...)` 顺序**逐字一致**）。
  ⇒ 落点：**裁定 15**（新增）· **FR-001** · **FR-004** · **SC-021**（新增）· Edge Cases
  · Key Entities。
  ⚠️ **顺带登记两处与上游的既有差异**（不影响本决定 · 供 **B22F1** 图渲染侧参考）：
  ① 上游 `Command` 是**泛型** `Command[Literal[...]]`（类型参数用于**图渲染**）⇒ freegraph 的

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 节点同时跳转与更新状态（Priority: P1）

作为用户，我希望我的节点**一边跳到下一个节点、一边把状态更新写进去** —— 两者**必须同时生效**，
不能只生效其一（更不能「跳转把更新吞掉」或「更新把跳转吞掉」）。

**Why this priority**: 这是本 feature 的**全部存在理由**（立项书 §5.2 B9F1 行的小目标逐字：
「`Command` 跳转 + 状态更新同时生效」）—— 没有它，`Command` 只是一个数据类型。

**Independent Test**: 一个节点返回 `Command(goto=END, update={"messages": [...]})` ⇒ 断言两条**同时**成立：
① 流程**按 `goto` 终止**（不再有新节点被触发）；② 最终状态**包含**该更新（且按归约器合并）。

**Acceptance Scenarios**:

1. **Given** 一个节点返回 `Command(goto=END, update={"messages": ["via-command"]})`，
   **When** 执行该图，**Then** 最终状态**包含** `"via-command"`，且流程**按 `goto` 终止**
   （`goto` 之后没有任何节点被执行）。
2. **Given** 一个节点返回 `Command(goto="next", update={"count": 1})`，**When** 执行该图，
   **Then** 节点 `"next"` **被执行**（跳转生效）**且** 状态里 `count` **被写入**（更新生效）
   —— 两条断言**同时**成立。

### User Story 2 - `Command` 的更新走归约器（Priority: P2）

作为用户，`Command.update` 里写的 `messages` 应与普通节点返回一样**按归约器合并**，
而不是**覆盖** —— 而且两种写法 MUST **逐项一致**（否则我会遇到「换个写法行为就变」的坑）。

**Why this priority**: 提示词 **§10** 的风险提示点名：若 `Command` 与普通返回值走**两条**合并路径，
迟早出现行为分叉（如「未知 key 报错」只对 `dict` 生效）。这条故事是那条风险的**正面防线**。

**Independent Test**: 同一份图规格、同一个 key，分别用「返回 `dict`」与「返回 `Command(update=)`」
写入 ⇒ 两者的**合并结果逐项相等**；再用一个 schema 外的 key ⇒ 两者**都**抛 `InvalidUpdateError`。

**Acceptance Scenarios**:

1. **Given** 一个归约型通道已有 `["a"]`，**When** 节点分别以「返回 `dict`」与
   「返回 `Command(update=)`」写入 `["b"]`，**Then** 两次的合并结果**逐项相等**（`["a", "b"]`）。
2. **Given** 同一个图规格，**When** 节点以两种写法写入一个**未知 key**，**Then** 两者**都**抛
   `InvalidUpdateError`，且 `invalid_keys` **一致**。

### User Story 3 - `Command.PARENT` 被识别但不越界（Priority: P3）

作为实现者，我希望 `Command.PARENT` 在 v1（**无子图**）时被**明确处理** —— 要么按普通跳转处理并给出
**可判定结果**，要么抛**明确异常** —— 而不是**静默失效**（流程悄悄跑偏、用户无从察觉）。

**Why this priority**: 提示词 **§3 P3** 逐字要求「行为可判定且有测试覆盖」；且 `__parent__` 与
用户自建的节点名可能**同名** ⇒ 不明确处理就会出现「跳到一个叫 `__parent__` 的用户节点」这种
**语义歧义**（宪法原则 VIII 的术语纪律）。

**Independent Test**: 传入 `Command(goto=Command.PARENT)` ⇒ 断言**显式失败**（点名 `__parent__`），

**Acceptance Scenarios**:

1. **Given** 一个节点返回 `Command(goto=Command.PARENT)`，**When** 执行该图，

   **MUST NOT** 静默忽略。
2. **Given** 一份**含**名为 `__parent__` 的节点的图规格，**When** 构造该规格，

### User Story 4 - 跳转目标写错时立刻报错（Priority: P4）

**Independent Test**: 让一个节点返回 `Command(goto="不存在的节点")` ⇒ 断言**显式失败**且错误消息

**Acceptance Scenarios**:

   **Then** 系统**显式失败**（类型错误），**MUST NOT** 把 `123` 当成字符序列拆开。

### User Story 5 - 跳转与既有边并存时两边都不丢（Priority: P5）

作为用户，我的节点既有**既定的下一站**、又想临时**改道**时，我希望两件事**叠加**而不是互相取消 ——
`goto` **不吞掉**原有边，原有边也**不吞掉** `goto`。

**Why this priority**: 这是「跳转语义落点」最容易走偏的一处：`goto` 若被实现成「覆盖静态边」，
就会与上游**实测**行为分叉；反之若被实现成「另造第三种触发源」，就会违反 H-1 的承接条款。

**Independent Test**: 节点 X 有静态边 X→Y，且 X 返回 `Command(goto="Z")` ⇒ 断言 **Y 与 Z**
在**下一轮**都被执行。

**Acceptance Scenarios**:

1. **Given** 节点 X 有静态边 X→Y 且返回 `Command(goto="Z")`，**When** 执行该图，
   **Then** **Y 与 Z** 在下一轮**都被执行**（叠加）。
2. **Given** 节点 X 在第 1 轮返回 `Command(goto="Z")`、第 2 轮返回普通 `dict`，
   **When** 执行该图，**Then** 第 2 轮之后 **Z 不再**因 X 被触发（`goto` 只对**最近一次执行**有效）。

### User Story 6 - 空命令是「无操作」而不是「报错」或「乱跳」（Priority: P6）

作为用户，我写了一个**什么都没干**的命令（两个槽位都是空的），我希望它**什么都不做** ——
既不报错、也不乱跳、也不写脏状态 —— 但这个节点**仍然算跑过了**。

**Why this priority**: L1 契约层已把「显式给了但内容为空」（`update={}` / `goto=()`）冻结为
「**该位不产生动作**」⇒ 运行期 MUST 照此执行；否则会出现「契约层说合法、运行期却抛错」的**分层分叉**。

**Independent Test**: 让一个节点返回「`goto` 与 `update` 均为空」的 `Command` ⇒ 断言
「零写入 + 零跳转 + 节点计入执行记录」三条同时成立。

**Acceptance Scenarios**:

1. **Given** 一个节点返回 `Command(update={})`，**When** 执行该图，**Then** 状态**无任何新增写入**，
   且该节点**计入执行记录**。
2. **Given** 一个节点返回 `Command(goto=(), update={})`，**When** 执行该图，**Then** 状态**无任何新增写入**
   且**无任何跳转**（流程按其余触发源继续）。

---

### Edge Cases

- **节点返回 `None`**（而非 `dict` / `Command`）⇒ MUST 视为**显式失败**（MUST NOT 静默当作「无写入」）。
- **节点返回 `list` / `str` / 其它类型** ⇒ MUST **显式失败**（类型错误）。
- **节点返回 `Command()`**（三槽位全未提供）⇒ L1 构造期即抛 `FreegraphError` ⇒ **运行期不可达**
  （MUST NOT 由运行期另造一条失败路径）。
- **`Command(update={})`** ⇒ **无写入**（该位不产生动作），节点仍计入执行记录。
- **`Command(goto=())`** ⇒ **无跳转**（该位不产生动作）。
- **`Command(goto=(), update={})`** ⇒ **无操作**（零写入 + 零跳转）。
- **`goto` 的目标订阅的通道都没值**（入参为空）⇒ MUST **照跑**（与静态边同款）⇒ 其入参为空 `dict`、但**不**因此被跳过（上游实测同款）。
- **`Command(goto="", ...)`**（空串）⇒ MUST **显式失败**（空串不是合法节点名，也不是终止标记）。
- **`Command(goto=Command.PARENT)`** ⇒ MUST **显式失败**（`NotImplementedError` · 子图属 v2 能力）。
  （⚠️ 与「目标名不存在」的 `ValueError` **可区分** · 澄清轮 Q2。）
- **`Command(goto="__start__")`** ⇒ MUST **显式失败**（`START` 不是合法跳转目标）。
- **`Command(goto="不存在的节点")`** ⇒ MUST **显式失败**（点名该目标）。
- **`Command(goto=123)` / `Command(goto=(x, 1))`**（非 `str` / 序列含非 `str`）⇒ MUST **显式失败**（类型错误）。
- **`Command(goto="a", goto="b")` 的多目标形态 `goto=("a", "b")`** ⇒ 两个目标**各自**成为下一轮的边触发源。
- **节点返回 `list[Command | dict]`**（命令列表）⇒ MUST **被接受**（上游同款）；各条命令按**列表顺序**依次生效（写入按序合并 · `goto` 各自成边）。
- **命令列表里混入 `dict` 元素** ⇒ MUST **被接受**（上游同款 · `_get_updates` 的 `else` 分支）⇒ 其写入按**所在位置**生效。
- **命令列表的元素类型非法**（如 `[1, 2]`）⇒ MUST **显式失败**（内置 `TypeError`）。
- **空命令列表**（`[]`）⇒ **明确无操作**（零写入 + 零跳转 · 节点仍计入执行记录）。
- **命令列表里含 `Command.PARENT`** ⇒ 与单条命令**同款**（`NotImplementedError` · 子图属 v2 能力）。
- **`Command(update=["a"])`**（`update` 非 `dict`）⇒ MUST **显式失败**（类型错误）。
- **`Command(update={"未知 key": 1})`** ⇒ MUST 抛 `InvalidUpdateError`，`invalid_keys` 列出**全部**未知 key。
- **`Command.update` 与同轮**其它**节点写同一个覆盖型通道** ⇒ MUST 抛 `InvalidChannelUpdateError`
  （与普通返回值**同款**）。
- **`Command.update` 的归约器抛错** ⇒ 异常 MUST **向上传播**，且**整轮**写入不合并（原子性）。
- **同一轮内两个节点都 `goto` 同一个目标** ⇒ 该目标在下一轮**只执行一次**（一个节点一轮内至多一次）。
- **`goto` 目标在下一轮已被别的触发源触发** ⇒ 仍**只执行一次**（两个触发源合流）。
- **`goto` 指向节点自身**（自跳）⇒ 下一轮再次被触发 ⇒ 由步数上限兜底。
- **`goto` 的目标名与某个通道 key 同名** ⇒ MUST NOT 混淆（触发源的**两个标识空间**分离 · 裁定 1）。
- **图规格里出现名为 `__parent__` 的节点** ⇒ **构造期**即 MUST 显式失败（保留名）。
- **`Command(resume="x")`** ⇒ MUST 被**接受**，且本 feature **不产生**任何恢复效果（写入 0 次、跳转 0 次）。
- **节点返回 `Command` 但同轮合并出错** ⇒ `goto` **不生效**（整轮失败 ⇒ 流程终止）。
- **`Command` 的 `update` 与节点的普通返回值在**同一轮**混用** ⇒ MUST 走同一条合并路径（顺序按节点表顺序）。
- **门面 `END` 的值与 L2 的终止标记字面量不一致** ⇒ MUST 被判据**自动核对**（SC-008）⇒ 不一致即判失败。
- **上游版本漂移** ⇒ 已核实的行号 MUST 在换版本后重新核实（宪法原则 VIII）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001（节点返回值：`dict` / `Command` / 命令列表，并列）**：系统 MUST 支持节点函数返回 `Command`
  （与返回 `dict` **并列**）；返回值 MUST 是 `dict`、`Command` 或 `list[Command | dict]` 之一；
  其它类型（含 `None`）⇒ MUST **显式失败**（内置 `TypeError` · 与 B7F1 的校验规则 **V-4** **同族**
  ⇒ 既有失败信号口径**不变**）。
  ⚠️ **`NodeSpec.run` 的返回类型注解 MUST 由 `Callable[[dict[str, Any]], dict[str, Any]]`
  放宽为「`dict[str, Any]` 或 `Command` 或 `list[Command | dict]`」** —— **只放宽「接受面」**
  ⇒ B7F1 契约 **§1** 的**构造签名与名字逐字不变** ⇒ B7F2 / B7F3 / B8F1 / B12F1 **零改动**。
  ⚠️ **命令列表**（澄清轮第 2 次 Q1 · 发起者拍板 · **上游同款**）：`list` 的元素 MUST 是
  `Command` 或 `dict`；元素为其它类型 ⇒ MUST **显式失败**（内置 `TypeError`）；
  **空列表** ⇒ **明确无操作**（零写入 + 零跳转 · 与裁定 10 的空槽位**同款**）。
  ⚠️ **V-4 的返回值口径随本条放宽**（`dict` / `Command` / `list`）—— 属**协变放宽**
  （**接受面**变大 ⇒ 对既有调用方**零破坏** · 与**裁定 11** 同款）。
  ⚠️ **L1 协议 MUST 与运行时一致**（**裁定 21** · 2026-11-11 分析轮 · **发起者特批**）：
  `freegraph.contracts.protocols.NodeFunc.__call__` 的返回联合 MUST **同步**放宽为
  `StateDict | Command | list[Command | StateDict] | None`（`StateDict` 即 `dict[str, Any]`
  ⇒ 与本条的 `list[Command | dict]` **逐字等价**）⇒ 否则「用 `NodeFunc` 标注的节点」在**类型层**
  无法表达列表返回 ⇒ **协议与运行时**出现分歧。
  ⇒ **L1 的符号集合与数量不变**（**18** 个 ⇒ **G7 恒绿**）· **MUST NOT** 改动其余任何 L1 符号的签名。

- **FR-002（`goto` 的落点 = B7F1 的「边触发源」空间 · 承接 H-1）**：`Command.goto` 表达的是
  「**下一个要执行的节点**」⇒ MUST 落在 B7F1 已冻结的**边触发源**空间（标识 `("e", 源节点名)`）
  ⇒ MUST **NOT** 另造第三种跳转语义、**MUST NOT** 引入第三类触发源标识。
  ⚠️ **落地口径**：执行 `goto` 的节点 X ⇒ 其**执行版本** +1（与普通执行同款）⇒ `goto` 的目标节点
  在**下一轮**以 `("e", X)` 这一**边触发源**被触发 ⇒ 与静态边 X→Y **同构**
  ⇒ 同一对 (X, Y) 在一轮内**至多触发一次**。
  ⚠️ **`goto` 目标的存储落点**（澄清轮 Q5 · 发起者拍板）：**调度状态对象**内的一个**带缺省值**的字段
  （B7F1 的 `SchedulerState`）⇒ `SchedulerState()` 的**构造签名与名字逐字不变**
  ⇒ **B7F2 / B7F3 / B8F1 / B12F1 零改动**（详见裁定 12）。
  ⚠️ **目标的触发与入参口径**（澄清轮第 2 次 Q3 · 发起者拍板 · 上游实测同款）：`goto` 的目标 MUST 在**下一轮**被触发（**无「有值」门槛** —— 与静态边**同款**：边触发源只比「源节点跑过没有」的版本号）⇒ 即使它订阅的通道**都没值**、入参为空，它**照跑**；其入参 MUST 是**正常稀疏读**的结果，读的是**上一轮合并后**的状态 ⇒ **读得到源节点本次 `update` 的内容**（详见裁定 17）。
  ⚠️ **与上游的一处差异（如实登记 · 非触发语义）**：上游节点默认读**整个 input schema**（稀疏），而 freegraph 的入参是「**订阅集 ∩ 有值集**」（B7F1 裁定 2 已冻结的**更窄**口径）⇒ **入参的「范围」两者不同**，但**「跳过去就跑」这个触发语义完全一致**。
  ⚠️ **跳转的「可观察出口」**（澄清轮第 2 次 Q4 · 发起者拍板 · 上游同款）：「跳到哪里去了」MUST **可观察**，但**MUST NOT** 为此给 `SuperStepResult` **增字段**（B7F1 的**四字段冻结面**）⇒ 证据 = ① **下一轮 `executed`** 里出现该目标节点 · ② **L1 的 `StateSnapshot.next`**（「下一轮要执行的节点名」· **逐字对应**上游 `types.py:688-689`）⇒ **两处已足**（详见裁定 18）。
  ⚠️ **`goto` 目标 MUST NOT 在同一轮内执行**（与静态边同款：下一轮才跑）。

- **FR-003（`goto` 与 `update` MUST 同时生效）**：`Command.goto` 与 `Command.update` MUST
  **同时生效**（跳转不吞掉更新、更新不吞掉跳转）；二者**互不排斥**、**无先后依赖**
  ⇒ 判定口径 = 一轮结束时「**跳转已登记为下一轮的边触发源**」与「**更新已按通道语义合并进状态**」
  两条断言**同时成立**（缺任何一条即判失败）。

- **FR-004（`Command.update` MUST 与普通返回值共用同一条合并路径 · 承接 H-2）**：`Command.update`
  的内容 MUST 与节点的普通 `dict` 返回值走**同一条写入路径**：逐 key 应用该通道的归约器；
  无归约器则**覆盖**；**未知 key ⇒ `InvalidUpdateError`**（**C6** · L1 已冻结 ·
  `invalid_keys` MUST 列出**全部**未知 key）。
  ⚠️ **「一条路径」是结构性的**：两种返回值 MUST 先被**归一**为同一份「待写入」，再交给**同一个**合并实现
  ⇒ MUST NOT 为 `Command.update` 另写一条合并实现 ⇒ MUST NOT 出现「未知 key 只对 `dict` 报错」
  「归约器只对 `dict` 生效」这类**分叉**。
  ⚠️ B7F1 的**批量**合并口径（每通道**一次** `Channel.update(values)`）与**原子性**口径
  （一轮要么全成、要么全不成）MUST **一并适用**于 `Command.update`。
  ⚠️ **多条命令的生效顺序 = 列表顺序**（澄清轮第 2 次 Q1 · 上游同款）：节点返回
  `list[Command | dict]` 时，MUST 按**列表顺序**把各条命令的 `update` 归入**同一份**待写入
  （⇒ 归约型通道按**列表顺序**归约 ⇒ 与上游 `_get_updates` 的 `updates.extend(...)` 顺序**逐字一致**）
  ⇒ **MUST NOT** 按 key 聚合后打乱顺序、**MUST NOT** 让「后一条命令覆盖前一条」。
  ⚠️ **多条命令的 `goto` 各自成边**：列表里**每条**命令的 `goto` MUST 各自成为下一轮的一条边
  ⇒ 目标**全部**在下一轮被触发（与「单条命令 + 多目标 `goto`」**同款**）。
  ⚠️ **写入的归属口径 = 源节点**（澄清轮第 2 次 Q2 · 发起者拍板 · 上游同款）：`Command.update`（及命令列表里的每条命令）的写入 MUST 归到**返回该命令的那个节点**名下（`node_writes` 的**按节点分组**）⇒ **B8F1** 的「本节点**本次**写入」fresh 读**读得到** ⇒ MUST NOT 归到合成节点、MUST NOT 只进最终状态（详见裁定 16）。

- **FR-005（`Command.PARENT` MUST 存在且被识别 · v1 行为可判定）**：系统 MUST 提供 `Command.PARENT`
  常量（L1 已冻结 · 值 = `"__parent__"`）；在 v1（**无子图**）其行为 MUST **可判定**：
  `goto=Command.PARENT` ⇒ MUST **显式失败**（**`NotImplementedError`** · 消息 MUST 点名
  `__parent__` 与「子图属 v2 能力」）⇒ MUST **NOT** 静默失效。
  ⚠️ **失败信号按「语义分类」分开**（澄清轮 Q2 · 发起者拍板）：**目标名不存在** ⇒
  **`ValueError`**（写错了 · FR-007）· **`Command.PARENT`** ⇒ **`NotImplementedError`**
  （**合法常量**、本版本**未实现子图**）⇒ 二者**语义不同** ⇒ 用户与下游 freechain 可分别捕获。
  ⚠️ **仓库同款用法**：`interrupt()`（`src/freegraph/_primitives.py`）与 `StateGraph` 的方法在
  **未接线**时都抛 `NotImplementedError` 并**点名归属的 feature** ⇒ 本条与之一致。
  ⚠️ **对 B7F1「一个 feature 只用两种内置异常（`ValueError` / `TypeError`）」不变量的刻意偏离**
  （第三种 = `NotImplementedError`）⇒ **已登记**（澄清轮 Q2 · 裁定 7）⇒ MUST NOT 被当成实现漂移。
  ⚠️ **`__parent__` 是「保留节点名」**：图规格里出现名为 `__parent__` 的节点 MUST **构造期显式失败**
  （内置 **`ValueError`** —— 属「规格写错了」· 与 B7F1 的 V-1 / V-2 / V-3 同族）
  ⇒ 杜绝「用户自建一个叫 `__parent__` 的节点 ⇒ `Command.PARENT` 跳到它」的歧义。
  ⚠️ **跨层传播（子图 → 父图）属 v2**（C26）⇒ 本 feature **MUST NOT** 实现它。

- **FR-006（「`Command` 但 `goto` 与 `update` 均为空」⇒ 明确无操作）**：节点返回 `Command` 而
  `goto` 与 `update` **均为空**（`goto` 为 `None` / 空序列 · `update` 为 `None` / 空映射）⇒
  MUST 是**明确无操作**：**零写入**、**零跳转**；该节点**仍计入执行记录**、其**执行版本**照常 +1；
  流程按其余触发源继续。
  ⚠️ 「未提供」（`None`）与「显式给了但内容为空」（`update={}` / `goto=()`）**严格区分**
  （L1 `Command` docstring 逐字）—— 两者在本条下**同归「无操作」**。
  ⚠️ 三个槽位**全**未提供（`Command()`）⇒ L1 构造期即抛 `FreegraphError`（**已冻结**）
  ⇒ 运行期**不可达**（MUST NOT 由运行期另造失败路径）。

- **FR-007（`goto` 的目标 MUST 可判定）**：`goto` 的目标 MUST 是「**节点表中存在的节点名**」
  或「**终止标记**」。
  ⚠️ **`str` MUST 先判 `isinstance(x, str)`**（`str` 本身也是 `Sequence[str]`
  ⇒ 顺序判断会把它拆成字符序列 —— L1 docstring 逐字点名）。
  ⚠️ **`Sequence[str]`** ⇒ **多个目标**（各自成为下一轮的边触发源 —— 澄清轮 Q4 · 发起者拍板；
  上游同款 · 已实测）；**空序列** ⇒ **无跳转**；
  非 `str` 元素 ⇒ MUST **显式失败**（内置 `TypeError`）。
  ⚠️ **目标不在节点表** ⇒ MUST **显式失败**（内置 **`ValueError`** · 消息 MUST 点名该目标
  —— 属「名字写错了」）⇒ MUST **NOT** 静默忽略。
  ⚠️ **与 `Command.PARENT` 的失败信号分开**（澄清轮 Q2）：本条是 `ValueError`（写错了）·
  `Command.PARENT` 是 `NotImplementedError`（合法常量 · 能力未实现）⇒ 见 FR-005。
  ⚠️ **终止标记** = 字符串 `"__end__"`（与门面 `END` **逐字相等**）⇒ `goto=END` ⇒ **不产生跳转**
  （该位不产生动作 = 「**这一位没有下一站**」）；**更新照常生效**。
  ⚠️ **`END` 不终止整张图**（澄清轮 Q3 · 发起者拍板）：其它触发源（静态边 / 条件边）照常推进
  ⇒ **图是否结束由「收敛」决定**（没有任何触发源了就停）⇒ 与上游同款（`graph/state.py:1771-1774`）。
  ⚠️ L2 **MUST NOT** import 门面（L3 · ARCH-1）⇒ 终止标记 MUST 以**字面量**判定
  ⇒ MUST **NOT** 自造新的终止标记值；门面 `END` 的值 MUST 与该字面量**逐字相等**（可自动核对）。

- **FR-008（`goto` 与静态边并存 ⇒ 叠加，不覆盖）**：节点 X 同时存在静态边 X→Y 且返回
  `Command(goto="Z")` ⇒ **Y 与 Z** MUST 都在**下一轮**被触发（**叠加**）；MUST **NOT** 让 `goto`
  取消静态边，亦 MUST **NOT** 让静态边取消 `goto`。
  ⚠️ **上游同款**（实测：`langgraph 1.2.11` 下静态边目标与 `goto` 目标**都**被执行）。
  ⚠️ **概念锚点（澄清轮 Q1 · 发起者拍板）**：「**Edge 是给框架和人看的，节点本身不知道 Edge 的存在**；
  而 `goto` 相当于 **Edge 在节点中的一个标签**」⇒ 静态边 = **框架层写死**的边 ·
  `goto` = **节点层自己声明**的边 ⇒ **两者同类** ⇒ 节点**没有**「取消框架那条边」的语义
  ⇒ **叠加**是自洽的（"顶掉"属特批语义 · freegraph 不自造）。

- **FR-009（`goto` 目标的生命周期 = 最近一次执行）**：节点 X 的 `goto` 目标 MUST 由 X 的
  **最近一次执行**决定；X 再次执行且**不**返回 `goto` ⇒ X 的 `goto` 目标 MUST 被**清空**
  ⇒ MUST **NOT** 留下上一次的残影；`goto` 只影响**下一轮**（MUST NOT 跨轮持续触发）。

- **FR-010（`Command.update` 的形态 MUST 合法）**：`Command.update` MUST 是 `dict`
  （L1 冻结的 `StateDict`）；非 `dict`（含 `None` 之外的任何类型）⇒ MUST **显式失败**
  （内置 `TypeError`）。
  ⚠️ `update=None` ⇒ 该位**未提供** ⇒ **无写入**（合法）。

- **FR-011（`resume` 本轮只被接受）**：`Command(resume=...)` MUST 被**接受**（不抛错）；
  本 feature MUST **NOT** 产生任何恢复效果（**不**写入任何通道、**不**产生跳转、**不**改变流程）
  ⇒ 恢复语义归 **B10F1**（下游承接 **D-2**）。

### Key Entities

- **`Command`（命令原语）**：节点可以返回的命令，承载三个语义位（`goto` / `update` / `resume`）——
  **类型**在 L1 冻结（`freegraph.contracts.types.Command`），
  **运行期语义**由本 feature 交付（`goto` = 跳转 · `update` = 状态更新 · `resume` = 本轮只被接受）。
- **`Command.PARENT`（保留标记）**：「跳向最近的父图」的字符串哨兵（`"__parent__"`）——
  v1 **无子图** ⇒ 显式失败；`__parent__` 同时是**保留节点名**。
- **节点返回值**：节点的产出，合法形态 = **`dict`（部分状态）**、**`Command`**（命令）或
  **`list[Command | dict]`**（命令列表 · 上游同款）—— 三者**并列**，且**共用同一条写入路径**；
  命令列表按**列表顺序**依次生效（写入按序合并 · `goto` 各自成边）。
- **待写入（pending writes）**：节点产出、**轮末统一合并**的写入；**按节点分组**保留
  （B7F1 FR-006）⇒ **`dict` 返回与 `Command.update` 在此归一为同一份数据**。
- **边触发源**：使节点被触发的东西之一（标识 `("e", 源节点名)` · 版本 = 源节点的**执行版本**）——
  **静态边**与 **`Command.goto`（动态边）**在触发源层面**完全同构**（裁定 1）。
- **动态边表（`dynamic_edges`）**：源节点 → 其**最近一次执行**给出的跳转目标；
  由源节点**再次执行**即刷新（无 `goto` ⇒ 清空）⇒ 运行期状态（落在调度状态对象内 · 裁定 12）。
- **终止标记**：字符串 `"__end__"`（与门面 `END` 逐字相等）⇒ `goto=END` ⇒ **不产生跳转**。
- **通道写入语义**：状态写入的唯一路径（逐 key 应用归约器 · 无归约器则覆盖 · 未知 key ⇒
  `InvalidUpdateError`）—— **`Command.update` MUST 走这一条**。
- **无效更新错误（`InvalidUpdateError`）**：**L1 契约层**冻结的**显式失败**信号 ——
  节点返回了状态 schema 中不存在的 key（**C6** · 结构化字段 `invalid_keys`）。
