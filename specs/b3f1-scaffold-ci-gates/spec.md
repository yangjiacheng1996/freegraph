### Session 2026-11-07

- **裁定 1（`requires-python` = `>=3.11`，引文 FR-003 的 `>=3.10` 作废）**：
  `requires-python` MUST 为 **`>=3.11`**。
  **依据**：宪法「运行时环境基线（Python 版本与 typing 构件上限）」——「**最低版本 = 3.11**：`requires-python` MUST 为 `>=3.11`」；宪法修订记录 **v1.2.0**（3.10 已于 2026-10 结束安全支持；且 `typing.Self` 是 3.11 才有的，原定 3.10 的理由「`Self` 在 3.10 起可用」**经实测不成立**）；立项书 §3.5「Python 最低版本 = **≥ 3.11**」与 **E18**；引文自身 **FR-001** 与 **SC-002b** 亦为 3.11。
  **推论**：引文 FR-003 的**唯一独立增量**（「**不设上限**」）予以保留 → 落 **FR-003**（`requires-python` MUST NOT 含任何上界）。

- **裁定 2（CI 矩阵最低档 = 3.11，引文 §2 / FR-012 的「3.10」作废）**：
  CI 矩阵的**最低版本档 MUST 为 3.11，且该档 MUST 跑全量测试（含架构门禁）**。
  **依据**：宪法 v1.3.0「判定口径」第 ① 条（「**主判定 = CI 最低档**：CI 矩阵的最低版本档 MUST 为 3.11，且**全量**跑测试（含架构门禁）」）；立项书 §3.5 CI 矩阵行；引文自身 **SC-002b**。
  **为何是主判定**：任何 3.12+ / 3.13+ 的 typing 构件在该档**天然不可用**（`ImportError` / `AttributeError` / `SyntaxError`）⇒ **不需要**额外的静态检查即可拦住；静态断言（**G9**）只用于给出**可读报错**（辅判定）。

- **裁定 3（CI 矩阵最高档 = 3.14 · **2026-11-07 澄清会话确认**）**：
  CI 矩阵的**最高版本档 = 3.14**。
  **依据**：立项书 §3.5「运行环境与支持矩阵」的 **CI 矩阵行**（「Linux + macOS + Windows × 最低版本（3.11）+ 最高版本（**3.14**）」）与**隔离验收环境行**（「Linux + Python 3.11 + **3.14**」）；仓库现状 `pyproject.toml` 的 classifiers 已列 `Programming Language :: Python :: 3.14`（**已入库的对外承诺**）。
  **反证据与取舍**：引文 §2 / FR-012 写「3.13」，且立项书 §3.5「Python 上限」行写「不设上限（仅在 CI 跑 3.13 验证）」——**同一张表内自相矛盾**。按「**§3.5 专门矩阵行（CI 矩阵行 + 隔离验收环境行）均写 3.14** > 同表泛化行（Python 上限行）的 3.13」的**专精性规则**裁定为 **3.14**（**实测 2026-11-07**：立项书中 `3.14` 出现 **2** 处、且**两处都是**专门矩阵行；`3.13` 出现 **3** 处、其中仅 1 处是泛化行、另 2 处是 typing 构件版本（`ReadOnly(3.13)` / `TypeIs(3.13)`）——故「出现次数多数」计票**不成立**，真正成立的是**专精性规则**）；**发起者已于 2026-11-07 澄清会话确认此取值**。
  **为何不阻断**：宪法只要求「**不设上限**」——最高档取 3.13 还是 3.14 **不是红线**，选 3.14 覆盖面更大且与已入库的 classifiers 一致。

  **补头位置的两条规则（与 FR-013 ② 一致）**：首行是 **shebang** ⇒ 头在 **shebang 之后**、docstring **之前**；首行不是 shebang ⇒ 头在**首行**、docstring **之前**（docstring 仍 MUST 是**首个语句**）。
  **依据**：宪法原则 X「**每一个源文件**（`src/` 下的包代码，以及仓库内的脚本）MUST 在文件顶部携带署名头」；引文 FR-013。

- **裁定 6（依赖红线的作用域 = freegraph 自身；门禁需要「两套断言」）**：
  **依据**：立项书 §9.2 与 **D12**（已批准 2026-11-05）——「**依赖红线的作用域 = freegraph 自身依赖闭包**（含隔离 venv 与运行时反向断言两套断言，**验收环境允许含脚本自带的 `langchain`**）」；宪法原则 I / II。
  > **📌 可判定环境 = 三个（2026-11-08 分析轮订正 · 已拍板 · 与 `contracts/dependency-gate.md` §1 逐字一致）**：
  > 立项书 / D12 的原文是「**两套断言**」（**保留**，那是**断言**的分类）；本 feature 的**可判定环境**拆成 **3 个**：
  > - **① 依赖断言环境 = 7/7 全装环境**（基础包 **+ 四个 extras 的传递依赖已安装**）⇒ **G21** 的递归展开才能走到闭包末端
  >   （G21 判据含「**未安装 ⇒ 判失败**」⇒ 在只装基础包的环境里**必红** ⇒ `contracts/dependency-gate.md` §1 已拆表登记）。
  >   断言：(a) 递归展开 freegraph 自身 `Requires-Dist`（**含全部 extras 变体**）无 `langsmith` / `langchain*` / `langgraph*` / **`deepagents`**。
  > - **② 隔离环境 = 只装基础包的隔离 venv**（零必装依赖）⇒ **G22** 断言：(b) 基础安装闭包 **== 空集** + `import freegraph` 后
  >   `sys.modules` 中无 `langsmith` / `langchain_core` / `langgraph`。
  > - **③ 验收环境** 装 freegraph + **脚本自带的** `langchain` 系 ⇒ **反向断言**：freegraph 运行期**从不** import `langchain` / `langchain_core`；freegraph 自身**零出站**。
  > ⇒ **「两套断言」= ① 的声明级闭包断言 + ③ 的运行期反向断言**（D12 原义不变）；② 是 ① 的**可判定前提分离**（隔离取证），**不新增断言口径**。
  **落点**：FR-005 ① / ② / ③；其中 **FR-005 ③**（验收环境的运行时反向断言）由门禁 **G22** 的「场景 ②」承担（`tasks.md` **T043** 落地 · **T042** 为其反向用例）——「环境里有 `langchain`」≠「freegraph 引入它」，二者 MUST 被分别断言。
  **⚠️ 分阶段落地（2026-11-07 分析轮 · 见 **裁定 22**）**：**B3F1 交付 FR-005 ③①（声明级 + 导入级）**；**FR-005 ③②（运行期 · 最小图）延后至 M2**（B6F1 建图 / B7F2 compile / B7F3 invoke 之后 —— 里程碑依据 立项书 §6.2）—— 理由：B3F1 属 M0 地基，内核运行时**尚未存在** ⇒ 「跑一段最小图」在 B3F1 **不可执行**。

- **裁定 7（零出站 = 只观测、不阻断 + 按发起方归因；只对「框架出站」断言 = 0）**：
  socket 监测夹具 MUST **只包装 `socket.connect` / `socket.create_connection`** 以**记录**目标与调用栈，并**放行**全部连接；**归因的机械判据见裁定 19**（「第一个非标准库帧」规则）；**只对「框架出站」断言 = 0**。
  **freegraph MUST NOT 安装、不启用任何出网拦截机制**——用户节点访问外网、调用真实模型、工具访问第三方 API 一律照常（**产品设计立场**，不是实现细节）。
  **依据**：宪法原则 V 门禁 4 与修订记录 **v1.0.0** 第 ② 条（措辞 PATCH，= **D12** 的组成部分）；立项书 §9.2 与风险 **R11**（「拦截式守卫与 freegraph 的产品定位冲突」）。

- **裁定 8（既有门禁 **G1–G20 零改动** · **唯一一处具名例外 = G3 的两处占位填充**）**：
  本 feature MUST NOT 修改既有门禁 G1–G20 的**判据**（含其硬编码文件清单）；本 feature 只**新增** G21–G30 并把既有门禁**接线**进 CI 流水线。

  > **⚠️ 唯一一处具名例外（2026-11-07 修订 · 须发起者追认后方可合入）**：
  > 既有门禁 **G3**（`tests/contracts/test_architecture.py`）的**两处占位** —— **判据句逐字不动**，只填充/修正占位内容：

  > - **净效果 = 变严**：白名单由 4 个**宽泛占位包名**变为**确切包名**；枚举由**过近似**变为**精确变体** ⇒ 符合 **FR-018**「不得放宽」；**MUST NOT** 引入任何新的白名单 / 豁免机制。
  > - **为什么必须改（实测结论 · 非推测 · 2026-11-07 复核）**：B3F1 MUST 声明 4 个 extras（FR-001 / FR-004）⇒ 既有 G3 的两条判据在 extras 声明后**必然失败**，且**失败的是哪一条**已实测澄清：
  >   - **实际变红的是「白名单子集断言」**（`extras <= CONSTITUTION_DEPENDENCY_WHITELIST`）：实测在**旧枚举语义**下 extras 闭包为 **20** 个包，其中 **8** 个不在 4 个占位包名内 —— `email-validator` / `furo` / `objgraph` / `opentelemetry-configuration` / `psutil` / `setuptools` / `sphinx` / `tzdata` ⇒ 子集断言**红**。

  >   - **`dnspython` 不在闭包内**（它是 `email-validator` 的依赖，而 `email-validator` 本身未安装 ⇒ 递归到 `email-validator` 时即取不到元数据）—— 故「`email-validator`（`Unlicense`）与 `dnspython`（`ISC`）二者」这一表述**不成立**（只有前者进闭包）。
  >   - **修正后的枚举语义（②）可实测复现**：按「只枚举 freegraph 自身的 extras 变体、传递依赖只展开其**基础**依赖」实测，extras 闭包**恰为**上表 12 个包名 ⇒ 与 ① 的 12 名白名单**逐一命中**、子集断言**绿**。
  >   - **G3 自己的 docstring 早已预告**（`tests/contracts/test_architecture.py:924-931`）：「extras **由 B3F1 引入**——本 feature 无 extras，该条**为空断言**」·「它在 **B3F1 引入 extras** 后立即变为**实质断言**」⇒ **填充时机就是 B3F1**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 破坏红线会立刻被拦住（Priority: P1）

作为项目发起者，我希望能保证任何人（人或 AI 代理）不小心把 `langchain-core` 加进 freegraph 的依赖声明、或在内核里 `import langchain` 时，**CI 立刻失败并指出是哪条规则**，而不是等到发版后才发现。

**Why this priority**: 本项目的核心资产是「**可审计的契约**」——零依赖红线、API 同名对齐。门禁不是配套工程，而是**契约的执行机制**；没有门禁，红线只是文档里的许诺。本 feature 排在 M0 最后，一旦生效即**守护后续 27 个 feature 的每一次提交**。

**Independent Test**: 在依赖声明里故意加入 `langchain-core`，CI 必须失败并输出违规条目（包名 + 命中的规则编号 + 修复指引）；撤销后恢复通过。**可独立验收，不依赖任何后续 feature。**

**Acceptance Scenarios**:

1. **Given** 仓库处于干净状态，**When** 在依赖声明中加入 `langchain-core` 后触发依赖门禁，**Then** 门禁**失败**，输出中含违规包名 `langchain-core` 与命中的规则编号，且**指明**该包是被哪条规则拦下的。
2. **Given** 依赖声明中引入了 `langgraph` 全系列 / `langsmith` 任一成员，**When** 触发依赖门禁，**Then** 门禁**失败**并逐条列出全部违规包（不只报第一个）。
3. **Given** 撤销了上述改动，**When** 再次触发依赖门禁，**Then** 门禁**通过**，且工作树**逐字未变**。

### User Story 2 - freegraph 自己不偷偷联网（Priority: P2）

作为用户，我希望能保证 freegraph 运行时不发起任何出站连接（连 `mermaid.ink` 也不发），而且这个保证是**可判定的**，不是口头承诺。

**Why this priority**: 「零出站」是 freegraph 对内网 / 离线 / 私有化部署用户的**核心价值承诺**；且它是「**可离线**」这一卖点的技术前提。承诺必须能自动判定，否则与「依赖红线」一样会退化成文档里的许诺。

**Independent Test**: 运行验收脚本时，socket 监测夹具记录的「**框架出站**」条目数为 **0**；用户代码主动发出的连接被**记录在案但判为通过**（不阻断、不判失败）。

**Acceptance Scenarios**:

1. **Given** freegraph 正常运行一段图，**When** 检查 socket 监测夹具的记录，**Then** 「框架出站」条目数 **== 0**，「用户出站」条目数可以 **> 0**（记录在案、不判失败）。
2. **Given** 用户节点内主动访问外部服务，**When** 该连接被建立，**Then** 连接**未被阻断**（freegraph MUST NOT 安装任何出网拦截机制），且被归因为「用户出站」。
3. **Given** 全部网络接口被置为不可用，**When** 重跑核心用例，**Then** 全部用例**通过**（freegraph 自身功能完整可用）。

### User Story 3 - 基础安装足够轻（Priority: P3）

作为内网 / 离线环境的用户，我希望能 `pip install freegraph` 只装上一个包（**零**第三方依赖），其余全部是可选 extra，需要时再装。

**Why this priority**: 「零第三方运行时依赖」是 README 的**对外承诺**，也是 D1 决议（契约层零依赖可独立消费）的收益前提。承诺必须可被断言，否则它只是营销话术。

**Independent Test**: 隔离 venv 中 `pip install freegraph` 后，第三方依赖闭包为**空集**（除 freegraph 自身与安装器自带的 `pip` / `setuptools` 外无任何包）。

**Acceptance Scenarios**:

1. **Given** 一个全新的隔离虚拟环境，**When** 只安装 freegraph 基础包，**Then** 环境内的第三方包数量 **== 0**（依赖闭包为空集）。

3. **Given** 不装任何 extra，**When** `import freegraph`，**Then** 导入**成功**且不产生任何第三方导入。

作为项目发起者，我希望能知道 M0 的三个 feature（B1F1 / B2F1 / B2F2）在**门禁建立之前**是否已经踩线——因为它们**没有被门禁守护过**。

### Edge Cases

- **依赖声明为空但 extra 变体有违规**：基础安装闭包干净 ≠ 全部 extras 闭包干净 ⇒ 递归展开 MUST 覆盖**全部 extras 变体**（**共 6 种**：基础安装 + 4 个 extra **各自单独**启用 + 4 个 extra **全部同时**启用 —— 定义见 Assumptions「extras 变体」），任一变体出现黑名单包即失败。
- **extras 之间的间接引入**：黑名单包**不**必须被 freegraph 直接声明——它可能由某个被允许的依赖**间接**拉进来 ⇒ 递归展开 MUST 走到闭包末端（而非只看一层 `Requires-Dist`）。
- **许可证明取不到 / 单一来源声明**：并非每个包都会老实地在元数据里写许可证——实测 `pydantic` 只写 PEP 639 的 `License-Expression`（`License` 字段与分类器皆空），也有包只随发行包附带 `licenses/` 授权文件。⇒ 证据链 MUST 按 **裁定 17** 的四级顺序读取，**MUST NOT** 因为「字段是空的」就判失败；反之，四级皆无 MUST 判失败并指名（静默放行 = 白名单失效）。
- **许可证标识的变体写法**：同一个宽松许可证常有好几种标识写法——`MIT` / `MIT-CMU` / `MIT-0` / `HPND`，`PSF` / `PSF-2.0`。白名单 MUST 只认 **5 个精确标识符**，变体**不放行**（原则 IX 为 NON-NEGOTIABLE）；被拒时 MUST 同时给出**包名**与**实测标识**，使「换个标识就能过」这条路被堵死。MUST NOT 用「等价对照表」或「家族判定」把红线稀释掉。
- **ELv2 组件点名**：`langgraph-api` / `langgraph-runtime-inmem` / Phoenix **额外点名**——它们不在通用黑名单前缀规则内，必须被显式名单覆盖。
- **门禁自身读环境变量**：门禁脚本在 CI 上运行时**会**读到 CI 环境变量（`CI` / `GITHUB_*` 等）⇒ 「内核不读环境变量」这条断言的**扫描域 MUST 限于 `src/freegraph/**`**，MUST NOT 扫门禁脚本与测试夹具（否则门禁会把自己判红）。
- **网络静态扫描命中可选 OTLP exporter**：`[otel]` 的 exporter 是**用户显式启用**才生效的合法出站方 ⇒ 静态扫描 MUST 把它**排除**在扫描域外（宪法：「可选的 OTLP exporter 仅在用户显式传入时生效」）⇒ **MUST 以显式名单表达**、MUST NOT 放宽扫描域本身（**⚠️ 该例外名单当前为空** —— OTLP exporter 属 **B21F1** · `contracts/architecture-gates.md` G26）。
- **socket 夹具的归因误判**：用户代码经由 freegraph 提供的回调间接发起连接时，调用栈**同时**含 `freegraph/` 路径与用户帧 ⇒ 若按「栈里有 freegraph 就算框架出站」会把**用户出站误判为框架出站**⇒ 门禁假红（用户脚本每次跑都红，门禁被当成噪声）。归因 MUST 按 **FR-009 ②①** 的「第一个非标准库帧」规则判定；「用户出站」**记录在案但不判失败**（宁可漏判为用户出站，不得把用户出站误判为框架出站）。
- **断网任务下的测试自身**：断网只影响**外部网络**；测试若依赖本地回环（`localhost`）MUST 在断网任务中仍可用，或该用例**明确排除**在断网任务之外（并记录排除理由）。
- **「必须能建立连接」的用例在断网下假红**：典型如「验证用户出站被归因为『用户出站』」这条——断网下连接必然失败，**失败原因不是 freegraph 的缺陷**。此类用例 MUST 落入**可机读的排除清单**并逐条写明理由（FR-010 ③④⑤），MUST NOT 因此被误判为「断网等价性失败」，MUST NOT 被顺手删掉或改断言绕过。
- **Windows 上的文件锁 / 路径分隔符**：门禁脚本 MUST 跨平台可运行（路径处理不依赖 POSIX 语义），否则矩阵的非 Linux 档位无法执行子集门禁。**CI 的解释器路径同样 MUST 跨平台**（**2026-11-08 分析轮订正**：Windows 上 `uv venv` 生成的是 `.venv\Scripts\` 布局 ⇒ 任何硬编码 POSIX 解释器路径都会让 `windows-2025` 的 2 个作业**每一条命令**路径失效 ⇒ **必红**，违反 PR-4）——具体写法见 `contracts/ci-matrix.md` §2（**只出现 venv 目录 `.venv`，MUST NOT 出现平台专属解释器路径**）。
- **工作树被污染的负向验证**：负向验证若中途异常退出，MUST NOT 留下被污染的工作树（见裁定 9）。
- **既有门禁的硬编码文件清单**：既有 G5 / G20 的扫描清单是**硬编码**的 ⇒ 新增源文件时**不会**被它们覆盖 ⇒ G30（全仓扫描）正是兜底；G30 MUST NOT 因此**放宽**既有 G5 / G20。

## Requirements *(mandatory)*

### Functional Requirements

#### A. 项目脚手架

- **FR-001**：系统 MUST 提供完整的项目元数据声明，其中：**基础运行时依赖为空集**（零第三方运行时依赖）、`requires-python` 为 **`>=3.11`**；**可选 extra 的依赖内容 MUST 取自宪法「依赖白名单 / 黑名单」· 包层白名单条原文所列**，MUST NOT 自行引入该白名单之外的包（各 extra 的具体内容见 **FR-004**；**`[otel]` MUST NOT 含任何 OTLP exporter** —— 见 **裁定 21**；**`[png]` = `playwright`** —— **宪法 v1.5.0 已列明**（原「mermaid 相关」的**类别式**表述**已被宪法 v1.5.0 取代**为确切包名），MUST NOT 另行引入第二个渲染后端）。
- **FR-002**：系统 MUST 采用 **`src/` 布局**（包代码位于 `src/<pkg>/`），且 MUST 发布**类型标记文件** `py.typed`（PEP 561），其内容 MUST 为空。
- **FR-003**：系统的 Python 版本区间 MUST **不设上限**——`requires-python` MUST NOT 含任何上界（仅含下界 `>=3.11`）。
- **FR-004**：系统 MUST 提供**可选 extra** 单元，且至少包含：`[pydantic]`（结构化状态 schema 支持）、`[checkpoint]`（checkpoint 序列化，依赖 `ormsgpack`）、`[otel]`（OpenTelemetry 可观测内核，依赖 **`opentelemetry-api`** 与 **`opentelemetry-sdk`**——**取宪法「依赖白名单 / 黑名单」· 包层白名单条原文所列**，**MUST NOT** 含任何 OTLP exporter，见 **裁定 21**）、`[png]`（本地 PNG 渲染，**后端 = `playwright`** —— **宪法 v1.5.0 已列明**，**默认关闭**）。
  - **FR-004 ①**：每个 extra MUST 是**独立可选**的——不装即不可用，且**基础安装 MUST NOT 拉起任何 extra 的依赖**。
  - **FR-004 ②**：`[png]` extra 的渲染后端 = **宪法 v1.5.0 已列明的 `playwright`**，且 MUST 同时满足：(a) **默认关闭**；(b) 依赖闭包 MUST 全部落在**许可证白名单** {MIT, Apache-2.0, BSD-2/3, PSF} 内；(c) **零出站**——MUST NOT 依赖任何远程渲染服务。（**2026-11-08 分析轮订正**：原写「具体渲染后端由 plan 决定」⇒ 已被宪法 v1.5.0 取代 ⇒ **plan 只核验许可证标识 ∈ 白名单与运行期零出站**，MUST NOT 另选后端。）
  - **FR-004 ③**：extra 的依赖声明 MUST NOT 引入任何黑名单包（见 **FR-005 ①** 的黑名单口径），且 MUST NOT 引入任何**传染性 / 限制性**许可证的包（见 **FR-006** 的许可证白名单）——该条覆盖**一切不在许可证白名单内**的标识符（含 `MPL-2.0`），这正是 `[otel]` 的 exporter 不可进本 feature 的原因（**裁定 21**）。

- **FR-005**：CI MUST 实现**依赖门禁**，其断言 MUST 同时覆盖**三个可判定环境**（裁定 6）：
  - **FR-005 ①（依赖断言环境 · 7/7 全装环境）**：递归展开 freegraph 自身声明的依赖（**基础安装 + 全部 extras 变体**），断言闭包中**无** `langsmith` / `langchain*` / `langgraph*` / **`deepagents`**（含子包与 provider 包，如 `langchain-core` / `langchain-anthropic` / `langchain-openai`）。**⚠️ 本条 MUST 在「extras 的传递依赖已安装」的环境里执行**（否则递归展开无法取证 ⇒ 按门禁自身规则「未安装 ⇒ 判失败」⇒ **必红** · `contracts/dependency-gate.md` §1 · 裁定 6 的 2026-11-08 订正）。
  - **FR-005 ②（隔离环境 · 导入副作用）**：在**只装基础包**的隔离 venv 中 `import freegraph` 后，`sys.modules` 中 MUST NOT 出现 `langsmith` / `langchain_core` / `langgraph`（并同时断言基础安装闭包 **== 空集**）。
  - **FR-005 ③（验收环境 · 反向断言 · 分阶段落地 · 裁定 22）**：在含**脚本自带** `langchain` 系的环境中，freegraph MUST NOT import `langchain` / `langchain_core`（运行环境里有 ≠ 被 freegraph 引入）。本条按**两段**落地：

#### C. 网络门禁（阻断 · 宪法原则 I）

- **FR-009**：CI MUST 实现**网络门禁**，由**两段**构成：
  - **FR-009 ①（静态扫描）**：`src/freegraph/**` MUST NOT 出现 `socket` / `requests` / `httpx` / `urllib.request` 等网络客户端调用（**扫描域一律以仓库内源码路径为准** —— 与 FR-007 ① 逐字一致；写 `freegraph/**` 在字面上指仓库根下的 `freegraph/` 目录 ⇒ **扫不到 ⇒ 空门禁**）；**例外** = 可选的 OTLP exporter 模块（用户显式启用才生效的合法出站方），该例外 MUST 以**显式名单**表达，MUST NOT 放宽扫描域本身。

    - **FR-009 ②②（该判据必须覆盖的四种栈形态）**：① freegraph 内部模块直接联网 ⇒ 判「框架出站」；② 用户工具函数联网、freegraph 只是**调用**了该用户函数 ⇒ 判「**用户出站**」（MUST NOT 误判为框架出站——否则用户正常用 AI 工具访问外网会每次把门禁打红）；③ 用户脚本直接联网 ⇒ 判「用户出站」；④ freegraph 直接使用 socket ⇒ 判「框架出站」。

### Key Entities

- **门禁（Gate）**：一条**可自动判定**的规则，具独立编号（既有 G1–G20 · 本 feature 新增 G21–G30）、独立执行入口、独立失败语义（退出码 + 可读报错）。门禁是「契约的执行机制」，不是文档条目。
  > **📌 术语消歧（2026-11-08 分析轮订正）**：本仓库「门禁」一词有**三个层级**，MUST NOT 混用——
  > **门禁编号（G1–G30）** ≡ 可自动判定的**检查**（本 feature 新增 G21–G30）；
  > **宪法质量门禁（1–7 项）** ≡ 合入前的**门禁清单项**（SC-003 所指的「7 项质量门禁」）；
  > **FR / SC** ≡ **需求条款 / 可测判据**。
  > ⇒ 引用时 MUST 带限定语（如「门禁 G9」「宪法质量门禁第 3 项」「FR-017」）。
- **层（Layer）L1–L6 与跨层单元**：代码的**归属层**（取值封闭于 L1–L6）；不属于任何单一层者（工程设施 / 发行与文档 / 公开 API 门面）记为「—」并标记为跨层单元。导入方向 = 依赖方向，**永远向下**。
- **依赖闭包（Dependency Closure）**：某个安装形态（基础安装 / 某一 extras 组合）下，freegraph 自身声明的依赖**递归展开**后的全部包集合。**基础安装的闭包 MUST 为空集**。
- **许可证明（License Evidence）**：某个依赖包的许可证标识与其来源字段；取不到即为**违规**（MUST NOT 静默放行）。
- **出站记录（Egress Record）**：一次连接尝试的**目标**（host:port）+ **调用栈** + **归因**（框架出站 / 用户出站）。只有「框架出站」参与断言。
- **依赖断言环境 / 隔离环境 / 验收环境**：**三个**可判定环境（裁定 6 · 2026-11-08 订正）。**① 依赖断言环境** = 7/7 全装（基础包 + extras 传递依赖已安装）⇒ 断言「freegraph 自身依赖闭包干净」；**② 隔离环境** = 只装基础包 ⇒ 断言「基础安装闭包为空集 + `sys.modules` 无 langchain 家族」；**③ 验收环境**额外含脚本自带的 `langchain` 系 ⇒ 断言「freegraph 运行期从不 import 它、且自身零出站」（该断言按 **FR-005 ③①②** **分阶段落地** —— B3F1 交付**声明级 + 导入级**，**运行期**部分**延后至 M2** · 见 **裁定 22**）。
- **extras 单元**：`[pydantic]` / `[checkpoint]` / `[otel]` / `[png]` —— 各自独立可选、默认不安装、依赖闭包受白名单约束。
- **签名头（Attribution Header）**：源文件顶部的署名声明（作者 · 许可证 · 项目地址）——它是 MIT「署名随文件流动」的兑现机制，也是「个人作品集」定位的机械保障。
- **自有品牌资产白名单（Own Brand Asset Allowlist）**：仓库内**允许存在**的**自有**图像 / 品牌色资产路径清单（FR-021 ②）——**第三方**品牌资产**一律禁止**（宪法原则 IX 第三条）；该白名单**当前为空集**。
- **负向验证用例（Negative Case）**：向被检对象注入一处**已知违规**，断言对应门禁**失败**；执行 MUST 不污染工作树。
- **分支保护 / required check**：仓库层面的**合并前强制点**——把 CI 的指定 job 列为「必过检查」，使「CI 失败 ⇒ 无法合并」成立。它把门禁的判定结果**接到**提交路径上；它**不是**门禁本身，也**不豁免**任何门禁判据。
