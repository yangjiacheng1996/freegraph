## 1. 逐条判定细则

### G1 · 顶层包惰性（继承）

**判定**：子进程执行 `import freegraph` 后，`sys.modules` 中**不含** `freegraph.contracts`
及其任何子模块。**必须子进程执行**——测试进程自身已导入 pytest，同进程 `sys.modules` 不可用。

### G2 · 契约层零内部 import + 零第三方 import（继承 · 范围扩展 · **两档范围**）

**判定**：AST 扫描，**两档范围**（B2F1 第二轮复核裁定 2026-11-06）：

| 档 | 扫描范围 | 判定 |
|---|---|---|
| ① **内部 import** | `src/freegraph/contracts/**/*.py` **+ `tests/contracts/**/*.py`**（含 `fixtures/`） | 不得出现指向 `freegraph` **顶层**或包外 `freegraph.*` 的 import（**包外相对导入**（`level >= 2`，如 `from ..runtime import X`）同样违规）；`freegraph.contracts` **内部**的导入**合法**——**相对导入**（`from .types import ...`）与**绝对导入**（`from freegraph.contracts import ...` / `from freegraph.contracts.protocols import ...`）**同等合法**（外部实现夹具只能写绝对导入，B2F1 复核补充） |
| ② **第三方 import** | `src/freegraph/contracts/**/*.py` **+ `tests/contracts/fixtures/**/*.py`**（**仅夹具目录**） | 不得出现 `langchain*` / `langgraph*` / `langsmith` / `pydantic` / `typing_extensions` / 任何非标准库顶层包 |

> **为何第三方档只扫夹具目录**：`tests/contracts/**` 的其余文件是**测试基础设施**，
> 必须 `import pytest`（开发期工具）才能驱动门禁；若把「任何非标准库顶层包」一刀切，
> 门禁会因 `import pytest` **恒失败**（B2F1 第二轮复核发现的口径缺陷）。
> 「夹具零内部依赖」这条判据**不受影响**——它由①档的**绝对导入白名单**保证。

> **本 feature 的范围扩展**：`tests/contracts/fixtures/external_impl.py` 必须**只** import
> `freegraph.contracts` ——「外部实现零内部依赖」这条判据因此**可被静态扫描判定**，
> 而不是靠人读代码（D-20）。

### G3 · 依赖闭包为空（继承）

**判定**：在**已安装** freegraph 的隔离环境中，递归展开 `importlib.metadata.requires()`
⇒ 基础安装闭包 **== 空集**。本地未安装时该用例 **skip**（不是失败）——口径同 B1F1。

### G4 · 零环境变量 + 零出站（继承 · 范围扩展）

**判定**：AST 扫描 `src/freegraph/contracts/**/*.py` **+ `tests/contracts/fixtures/**/*.py`**，
**不得**出现 `os.environ` / `os.getenv` / `socket.*` / `urllib.*` / `http.*` 的使用。

> **测试夹具同样受检**（夹具不得为了「假装能联网」而 import 网络库）——
> 夹具目录在扫描范围内（B2F1 第二轮复核裁定：原先「夹具同样受检」只有文字、无任务与实现支撑）。
> **其余测试文件豁免 G4**：`tests/contracts/test_architecture.py` 必须用 `subprocess` /
> `os.environ` 驱动子进程门禁（子进程隔离是 G1 / G3 的判定前提），对其扫描会**恒失败**。

### G5 · 署名头（继承 · 范围扩展）

**判定**：本 feature 新建的**每一个** `.py`（含 `tests/` 下的测试与夹具）首行逐字等于
`# Copyright (c) 2026 杨家成 · MIT License · https://github.com/yangjiacheng1996/freegraph`，
且**模块 docstring 是首个语句**。例外清单沿用宪法（`py.typed` / `harness/demo/target.py`）。

### G6 · `py.typed`（继承）

**判定**：仓库根 `src/freegraph/py.typed` 存在且**大小为 0**。本 feature **不新建**——
顶层一个即覆盖全部子包（D-01）。

### G7 · 公开符号面恰为 18 个（**修改**）

**判定**：`freegraph.contracts.__all__` 与
`specs/b2f1-contracts-protocols/contracts/public-api.md` §0 的符号清单**集合相等**
（多一个 / 少一个都失败）。**集合断言**才能抓住「偷偷多导出一个」。

**落地分两段**（B2F1 第二轮复核裁定 2026-11-06 —— 既有 G7 硬编码「恰 8 个」，
自第一次追加导出起必然失败，故 MUST 在导出开始**之前**就完成改造）：

| 段 | 断言 | 启用时机 | 抓什么 |
|---|---|---|---|
| ① **子集段** | `set(__all__) ⊆ §0 解析出的 18 个` | **始终启用**（Foundational） | 「偷偷多导出一个」——构造期 `__all__` 尚未齐全时恒成立 |
| ② **集合相等段** | `set(__all__) == §0 解析出的 18 个` | **全部 18 个符号导出后**（US5 末段） | 「漏导出」 |
| ③ **新增集合段** | §0 按**分组注释**切分出的「新增集合」== **FR-012 所列的 10 个**（`NodeFunc` / `Checkpointer` / `TraceSink` / `Store` / `CompiledGraph` / `Graph` / `Node` / `Edge` / `Span` / `TraceQuery`），且「既有集合」恰为 **8** 个 | **始终启用**（Foundational · T008） | 「新增面多一个 / 少一个」——**SC-017 的机械落点**（总集合相等断言**不覆盖**这一维） |

> **③ 的切分依据**：`public-api.md` §0 的**分组注释行**（「B1F1 已冻结的 8 个」/「B2F1 新增的 10 个」）——
> 切分逻辑与解析逻辑同处 T008 的辅助函数，**不得**在两处各写一份。
> **② 与 ③ 并存**：② 判「总数与内容」，③ 判「新增/既有的分界」——二者**不可互相替代**。

> **变更**：B1F1 的 G7 断言「恰 8 个」（硬编码常量 `PUBLIC_SYMBOLS`）；本 feature 改为
> 「**按清单解析**」——期望值从 `public-api.md` §0 读取（而非硬编码在测试里），
> 清单变、断言自动跟随，杜绝两处漂移。**硬编码常量与三处「恰 8 个」的陈旧注释
> MUST 一并清除**（含 `Send` / `interrupt` 归属注释：归 **v2**（B11F1 / B10F1））。

### G8 · 文档合规门禁（**修改**）

**判定**：① `THIRD_PARTY_NOTICES` 存在（且 §2 无**本 feature 新增**的运行时依赖登记 ——
零新增依赖 ⇒ 无需登记）；② `README.md` 的「API 兼容矩阵」章节**逐符号**覆盖
`public-api.md` §0 所列的全部符号（期望值从 §0 **解析**，**不得**硬编码 18；
**并按 §0 的分组注释切分出「既有 8 行」与「新增 10 行」**——切分逻辑与 G7 共用同一辅助函数）：
每个符号在矩阵中**恰有一行**，且该行含「对应上游符号 / 等价程度 / 差异说明」三列。

**落地分两段**（B2F1 第五轮复核裁定 · 2026-11-06 —— 与 G7 同构）：

| 段 | 断言 | 启用时机 | 抓什么 |
|---|---|---|---|
| ① **子集段** | 矩阵**当前已存在的行**逐条判定：首列符号 ∈ §0 的 18 个；行数 ≤ 18；每行含三列；「行内来源行号」只对**已存在的**新增行成立 | **始终启用**（Foundational · T008） | 「清单外符号」/「重复 / 超量」/「列数不足」/「来源不合规」 |
| ② **集合相等段** | 矩阵首列符号集合 == §0 解析出的 18 个 | **README 补入本层 10 行后**（T033） | 「漏写」 |

> **取行范围（2026-11-06 第六轮复核修订）**：两段都**只在 `README.md` 的「## API 兼容矩阵」
> 章节内取行**（复用既有 `COMPAT_MATRIX_PATTERN` 的章节解析）——**MUST NOT** 扫全文，
> 否则 README 其它章节里任何以 `| \`符号\`` 开头的表格行都会被误判为矩阵行
> （`quickstart.md` §2.5 的脚本亦按此口径同步修订）。
>
> **列数与来源落位（2026-11-06 第六轮复核裁定）**：兼容矩阵**保持 4 列**
> （既有 8 行**逐字不动** ⇒ 同表列数必须一致，**MUST NOT** 为来源单开一列）；
> 「有上游同名符号者」的来源行号（`路径:行号`）**写进该行的「差异说明」单元格末尾**
> （与说明文字以 `；` 分隔）。

> **为何必须分两段**：README 的本层 10 行由 **T033**（US4）写入，而 G8 的改造在 **T008**
> （Foundational）——若在 T008 就按「18 个符号逐个恰有一行」判定，T008~T033 之间
> README 只有既有的 8 行 ⇒ **门禁恒红** ⇒ 阶段 2 与阶段 6 的 Checkpoint 全都不可能绿。
> 与 G7 的两段落地**同构**（G7：子集段 T008 / 集合相等段 T040）。
> **两段共用 T008 的 §0 解析函数**，切分逻辑**只写一份**。
**「行内须含上游来源行号」这一子项只对本 feature 新增的 10 行中「**有上游同名符号**者」
成立**——既有 8 行按 FR-017 **逐字不动**，其上游来源以矩阵章节的**「证据来源」小节**为准
（B2F1 复核裁定：原判据要求 18 行全部行内带行号，与 FR-017「既有 8 行逐字不动」
直接冲突 ⇒ G8 必然失败）。

> **无上游同名符号者怎么写**（B2F1 第二轮复核裁定 2026-11-06）：本层 10 个符号中，
> `NodeFunc` / `TraceSink` / `Span` / `TraceQuery` **在上游没有同名符号**
> （上游对应物是「以普通 dict 调用的节点函数」、LangChain 的 `callbacks` / `tracers`、
> `RunTree` 之类的**非同名**物）⇒ 该行的「对应上游符号」列 MUST 写
> 「**无上游对应**（自由设计）」，差异说明列注明**契约条目号**
> （C5 / C6、C23 / C24、C27），**MUST NOT 硬凑行号**（凑一个不相干的上游位置会
> 污染证据纪律，违反宪法原则 VIII）。
> 对齐：spec **SC-021** / **FR-017** / `public-api.md` §1.1 与 §5 第 11 条**同一口径**。

> **变更**：由「覆盖全部 8 个符号」改为「**按清单逐符号**覆盖」——本 feature 起该断言
> **即可启用**（兼容矩阵的**本层 10 行已在本 feature 补入**，见 FR-017 / SC-021），
> 期望值随 `public-api.md` §0 自动跟随。全库矩阵的**补全与定稿归 B24F1**。

### G9 · 运行时环境基线（继承）

**判定**：AST 扫描 `src/freegraph/**/*.py`，显式点名 3.12+ / 3.13+ 的 typing 构件
（`TypeAliasType` / `override` / `ReadOnly` / `TypeIs` / PEP 695 `type` 语句）并给出
**可读报错**（指明「你用了 3.12+ 的 X」）。主判定 = **CI 最低版本档 3.11 跑全量测试**。

> **本 feature 的新增面**：`protocols.py` 用到的 `Protocol` / `runtime_checkable`（3.8+）、
> `graph.py` / `trace.py` 用到的 `dataclass`（3.7+）与 `Mapping` / `Sequence`（3.9+）——
> **全部 ≤ 3.11**，G9 无需放宽。

### G10 · 协议纯抽象（**新增**）

**判定**：AST 扫描 `src/freegraph/contracts/protocols.py` —— 5 个协议类体内的方法
**方法体必须只有 `...`**（`ast.Expr` 包裹的 `ast.Constant(Ellipsis)`）。出现
`pass` / `raise NotImplementedError` / 任何赋值或返回语句 ⇒ **失败**。
**构造期口径**：协议类尚未落地时（扫描结果为空）⇒ 判为**通过**；协议类一旦出现即自动受检。

> **落地位置**（B2F1 第四轮复核裁定 · 2026-11-06）：本门禁在 **Foundational 阶段的 T059** 落地
> （原排在 US5 末的 T042）——FR-007「协议 MUST 为纯抽象」是 MUST 级约束，而默认实现会让
> 「只声明部分方法」的假实现**静默通过**结构化子类型判定；若等到 US5 末才落地门禁，
> T011–T039 写协议期间**无任何自动判据**。自检亦随 T059 一并交付。

**理由**：默认实现会让「只声明部分方法」的假实现**静默通过**结构化子类型判定，
把「缺实现」这一真实缺陷掩盖到运行时（spec FR-007）。

### G11 · 结构化子类型判定可用（**新增**）

**判定**（运行时证据，三项）：

1. 五个协议均可做 `isinstance(obj, Proto)` 判定（`runtime_checkable` 生效）；
2. 用 `tests/contracts/fixtures/external_impl.py` 的**完整实现**逐个判定 ⇒ **全部为真**；
3. 对每个协议构造一个**缺任一方法**的实现 ⇒ 逐个判定 **全部为假**。

**已知局限（须写进 docstring 与本门禁说明）**：结构化子类型判定**只比对方法名存在性**、
不比对签名 ⇒「签名写错」判不出来，由**静态类型检查**承担（见 `research.md` D-19 的
mypy 路径与 `get_type_hints` 兜底断言）。

> **方法集一律以「集合相等」判定，MUST NOT 断言成员的定义顺序**
> （2026-11-06 第六轮复核裁定）：`typing.Protocol` 的成员集合是 `set`
> （CPython 3.11 / 3.12 实测：`{'c','b','a'}`），其迭代顺序随 `PYTHONHASHSEED` 变化
> ⇒ 按序断言必然 flaky。「成员定义顺序」亦 **MUST NOT** 纳入冻结面（spec FR-007）。

### G12 · 公开符号面唯一权威（**新增**）

**判定**：扫描仓库内的 `**/public-api.md`，读取其**首行附近**的机器标记
`<!-- authority: yes -->` / `<!-- authority: no -->`——标记为 `yes` 的文件数 **== 1**，
且该文件 MUST 是 `specs/b2f1-contracts-protocols/contracts/public-api.md`。

> **为什么用标记而不是关键词**：B1F1 的同名文件作为**历史快照**保留，其正文里仍含
> 「唯一手工维护点」「权威来源」等**字样**——用关键词判定会把它误计为权威（数出 2 个），
> 门禁恒失败。故判定**只认机器标记**，字样仅供人读。
> **标记缺失**时按「**非权威**」处理并在报错中点名该文件（MUST NOT 静默通过）。

**理由**：本 feature 新建同名文件后，B1F1 的旧文件若仍自称权威，读者会取到过期清单
（spec Q10 / Q13 · SC-020）。B1F1 的旧文件顶部加**一行取代提示**（不删改既有内容），
其正文作为 B1F1 的**历史快照**保留。

### G13 · 纯数据纪律（**新增**）

**判定**：以 `typing.get_type_hints` 解析 `Graph` / `Node` / `Edge` / `Span` / `TraceQuery`
的字段注解，字段类型 MUST 落在**白名单**之内：

| 允许（白名单） | 说明 |
|---|---|
| `str` / `int` / `float` / `bool` / `None` | 标量 |
| `Mapping[str, Any]` | 映射（`Node.metadata` / `Span.attributes` / `Span.context`）——`Any` **仅允许**出现在其**值位** |
| `tuple[...]` | 不可变元组（`Graph.nodes` / `Graph.edges`） |
| 本层纯数据类 | `Node` / `Edge` / `Graph` / `Span` / `TraceQuery`（纯数据类之间的组合） |

**失败条件**（任一成立即失败）：① 字段类型落在白名单之外；② 出现**可调用类型**
（`Callable` / `Protocol` / 任何含 `__call__` 的类型）；③ `Any` 出现在白名单所列位置**之外**
（如 `attributes: Any`、`metadata: list[Any]`）；④ 字段名表明它装的是**对象引用**
（判据：字段类型不是「标量 / 映射 / 序列 / 元组 / 本层纯数据类」）。

> **为什么改成白名单**（B2F1 第四轮复核裁定 · 2026-11-06）：原判据写「不得出现…任意
> **对象实例类型**」——该类别在 `get_type_hints` 口径下**不可机械判定**（`Any` 是否算
> 「对象实例类型」无定论），而 `Mapping[str, Any]` 又是**已冻结的合法字段**。
> G13 是**冻结面**（「改判定方式 = 改冻结面」），故判据本身必须**可执行且唯一解**——
> 白名单形式满足该要求，且**不放松**原纪律（对象引用字段仍然失败）。

**理由**：本项目「纯数据 + 纯数据类」纪律的**可执行化**——上游 `langchain_core` 的
`Node.data` 装的是可调用对象 / pydantic 对象（`langchain_core/runnables/graph.py:102`），
freegraph MUST NOT 重蹈（spec FR-006 · D-09）。
