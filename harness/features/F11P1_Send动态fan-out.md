## 提示词正文

### 1. 目标

交付 `Send` 原语：**动态 fan-out**。条件边（或节点）可以返回一个 `Send` 列表，
每个 `Send` 指定「调用哪个节点」与「**用自定义入参**调用它」——从而实现 map-reduce
模式：同一个目标节点被并发调用多次，每次拿到不同的输入。本 Phase 的判定是：
**map-reduce 模式可运行**。

### 2. 背景与上下文

- **C18（动态 fan-out）**：`Send(node, arg)`——以自定义 arg 调用目标节点。
  Q8 把 `Send` 标注为「通用语义」，freegraph 提供自有实现。
- `Send` 与静态边的区别：静态边 `add_edge(src, dst)` 总是用**同一份状态**调用 `dst`；
  `Send` 允许**每次调用带不同的入参**，这是 map-reduce 的核心。
- 验收脚本已锁定调用形态（`harness/demo/graph_core.py`）：
  条件边返回 `[Send("worker", {"n": 1}), Send("worker", {"n": 2})]` → 目标节点被调用
  两次，且分别收到 `{"n": 1}` 与 `{"n": 2}`。
- **v1 的 `Send` 目标节点入参形态**：MUST 能表达「自定义入参」这一核心语义；
  与「完整状态 + 自定义入参」的组合形态若纳入，须在 spec 中写明。

### 3. 用户场景

**P1 — 同一节点被多次调用，入参不同**
作为用户，我有一个 `worker` 节点要处理 2 个不同的任务，我希望它被调用两次，
每次拿到自己的任务参数。

- **独立验收**：`worker` 的副作用计数 == 2，且两次收到的入参分别是 `{"n": 1}` 与
  `{"n": 2}`。

**P2 — fan-out 的结果汇合**
作为用户，多个 worker 的产出应按归约器汇合到同一状态 key，从而得到汇总结果。

- **独立验收**：汇合通道的最终值 == 两次产出的归约结果。

**P3 — 没有 `Send` 时行为不变**
作为用户，普通静态边的执行行为 MUST 与引入 `Send` 之前一致。

- **独立验收**：静态边用例回归通过。

### 4. 功能需求

- **FR-001**：系统 MUST 支持条件边（及节点）返回 `Send` 对象或 `Send` 列表。
- **FR-002**：系统 MUST 支持 `Send(node, arg)`：指定目标节点名与**自定义入参**。
- **FR-003**：系统 MUST 以每个 `Send` 的自定义入参调用其目标节点；多个 `Send` 指向
  同一节点时 MUST 产生**多次独立调用**。
- **FR-004**：由 `Send` 产生的调用 MUST 与普通节点调用**共用同一条状态写入合并路径**
  （C6）。
- **FR-005**：系统 MUST 明确「`Send` 的目标节点不存在」时的行为（明确异常），并在
  spec 中写死。
- **FR-006**：系统 MUST 明确「普通边与 `Send` 混合」时的调度语义（例如同一 super-step
  内既有静态边触发又有 `Send` 任务），并在 spec 中写死。
- **FR-007**：系统 MUST NOT import `langchain` / `langchain-core`；MUST NOT 读环境变量。

### 5. 成功标准

- **SC-001**：`Send` fan-out 用例：目标节点执行次数 == `Send` 数量，且各次入参正确。
- **SC-002**：fan-out 产出的状态按归约器汇合，结果 == 预期归约值。
- **SC-003**：静态边用例回归通过（引入 `Send` 不改变既有行为）。
- **SC-004**：`Send` 目标不存在时抛出明确异常（可由异常类型与消息判定）。

### 6. 验收判据（= 立项书 §5.2 F11P1 小目标，逐条可判定）

> 小目标原文：map-reduce 模式可运行

| # | 判据 | 判定方式 |
|---|---|---|
| A1 | map-reduce 模式可运行 | 用例：条件边返回 2 个 `Send` → 目标节点执行 2 次、入参各自正确 |
| A2 | 产出按归约器汇合 | 汇合通道最终值断言 |
| A3 | `Send` 目标节点不存在时**明确报错** | 断言抛出异常且消息指明目标节点名（不静默丢弃该 `Send`） |

### 8. 边界（本 Phase 明确不做）

- 不实现 `Command.PARENT` 的子图跨层 fan-out（属 v2 / C26）。
- 不实现 async（v2 范围）。
- 不实现 `recursion_limit`（属 F13P1）。
- 不实现 checkpoint（属 F14P1）。
- 不实现 `Send` 与 checkpoint 的 pending writes 持久化（属 F14P1）。
- 不实现 LangChain 的 `defer` / `task` 机制（不在 v1 范围）。

### 9. 红线与质量门禁

- **依赖门禁（阻断，红线）**：无 `langsmith` / `langchain*` / `langgraph*`。
- **零出站 / 零环境变量**。
- **ARCH-1**：L2 只依赖 L1。
- **契约门禁**：MUST NOT 破坏 C4 / C6 / C8；本 Phase 与 F12P1 的并发语义共同决定
  fan-out 的并发行为（spec 中须写明二者关系）。
- **人工门禁**：`harness/features/<feature>/manual-verification.md`。
- **证据门禁**：与 LangGraph `Send` 的对应须标注源码行号（`langgraph/types.py:704-720`）。

### 10. 交付物与后续

- **交付物**：`Send` 运行期语义（fan-out 任务生成与调度）、map-reduce 用例、
  单元测试 + 人工验证记录。
- **后续解锁**：**F13P1**（收口项）→ M2 全部 Phase。
- **风险提示**：`Send` 的**入参形态**（自定义 arg 替代完整状态，还是与完整状态合并）
  是一个会外溢到用户代码的接口决策——一旦定下，freechain 的 map-reduce 写法随之
  确定。spec 阶段必须把它**写死**，而不是留给 plan 阶段。
