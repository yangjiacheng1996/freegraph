## 提示词正文

### 1. 目标

交付**本地 trace 的读取侧**：一个**查询 API**（按 `thread_id` / 时间 / 节点名检索）
和一个 **SQLite 后端**（标准库 `sqlite3`，零第三方依赖），让用户能**按条件检索**
历史运行轨迹。本 feature 的判定是：**可按 thread / 时间 / 节点名检索**。

### 2. 背景与上下文

- **三件套之第 ② 件的完成态**：B20F1 解决「写」，本 feature 解决「查」。
  用户场景（立项书 §5.8.2）：查一次运行的全部 trace（定位哪一步慢、哪一步报错、
  模型收到什么）；按 thread 查多轮会话；**写自动化断言**（CI 中断言「每次运行恰好
  2 次模型调用」）。
- **SQLite 用标准库**：Python 自带 `sqlite3`——**不是第三方依赖**，不破零依赖承诺。
  B15F1（`SqliteSaver`）同理。
- **数据访问边界**（立项书 §5.8.4）：未来的 Studio 子包**只能通过查询 API 取数**，
  **不得**直连 SQLite 表或 JSONL 文件格式——否则 schema 一变 UI 即坏。
  → 因此本 feature 的查询 API MUST 是**稳定的对外接口**，且 MUST 明确「表结构 / 文件
  格式是内部实现细节」。
- ✅ **缺口 1 已关闭（D11 批准 2026-11-05）**：查询的**请求 / 返回结构**已随
  **C27** 冻结（见 §7）。

### 3. 用户场景

**P1 — 按 run 精确回查某一次运行**
作为用户，我刚跑完一次运行，手里有一个 `run_id`（从 `stream()` 事件或 trace 记录里读到），
希望用它把**这一次运行**的全部 span 精确取出——把每个节点视作微服务时，这就是
「链路监控的唯一通行证」。

- **独立验收**：写入 2 次运行（不同 `run_id`）的 trace，按 `run_id` 查询只返回该次运行
  的全部记录（含其所有节点 / 工具 / 模型 span）。

**P1b — 按 thread 查一次会话的全部 trace**
作为用户，我跑完一轮多轮对话，希望按 `thread_id` 把这次会话的所有 span 拉出来，
复盘整个过程。

- **独立验收**：写入 2 个 thread 的 trace，查询 thread-1 只返回 thread-1 的记录。

**P2 — 按时间范围定位一次运行**
作为用户，我希望按时间窗过滤，找出「昨天 14:00 那次运行」。

- **独立验收**：时间窗查询返回窗内记录、排除窗外记录。

**P3 — 按节点名查最慢的那一步**
作为用户，我怀疑某个节点慢，希望只查该节点的 span。

- **独立验收**：按节点名过滤返回对应节点的记录。

**P4 — 在 CI 里写断言**
作为用户，我希望用查询 API 在自动化测试中断言「本次运行恰好 2 次模型调用」。

- **独立验收**：查询结果可直接用于断言（返回结构稳定、可 JSON 序列化）。

### 4. 功能需求

- **FR-001**：系统 MUST 提供**查询 API**，支持至少**四类**过滤条件：**`run_id`**、
  `thread_id`、时间范围、节点名；四者**可组合**（C27）。
  > **`run_id` 是运行级检索的入口**（把每个节点视作一个微服务，则 `run_id` 是链路监控的
  > 唯一通行证）——按 `run_id` 查 = 精确回查某一次运行的全部 span。
  > `run_id` 由**运行时生成、用户不可设置**（C22 字段约定），因此它不是用户传入的
  > 查询条件，而是**先从 `stream()` 事件或 trace 记录里读到、再拿去查**。
- **FR-002**：查询结果 MUST 为**可 JSON 序列化**的结构（纯数据，不含不可序列化对象）。
- **FR-003**：系统 MUST 提供 **SQLite 后端**（标准库 `sqlite3`），作为本地 trace 的
  持久化与查询后端之一。
- **FR-004**：SQLite 后端 MUST 与 B20F1 的 JSONL 后端**接口一致**（可替换），使用方
  MUST NOT 感知具体后端。
- **FR-005**：查询 API MUST 是**稳定的对外接口**；表结构与文件格式 MUST 被视为
  **内部实现细节**（立项书 §5.8.4 的数据访问边界）。
- **FR-006**：查询结果 MUST 按**可判定顺序**返回（默认按时间升序；顺序 MUST 在
  spec 中写死）。
- **FR-009**：查询 API MUST 接受**空过滤器**（返回该存储中的全部记录，上限与排序策略
  MUST 在 spec 中写死），且 MUST NOT 因此报错。
- **FR-007**：查询 MUST 零出站；MUST NOT 读环境变量。
- **FR-008**：系统 MUST NOT import `langchain` / `langchain-core`。

### 5. 成功标准

- **SC-001**：按 `run_id` / `thread_id` / 时间 / 节点名**四类**过滤各有一例正确
  （可逐项判定）。
- **SC-002**：四类过滤**组合**使用结果正确。
- **SC-003**：查询结果 100% 可 JSON 序列化（可直接用于 CI 断言）。
- **SC-004**：JSONL 后端与 SQLite 后端对**同一份查询**给出**等价结果**（可替换性判定）。
- **SC-005**：零出站、零环境变量读取。

### 6. 验收判据（= 立项书 §5.2 B20F2 小目标，逐条可判定）

> 小目标原文：可按 thread / 时间 / 节点名检索

| # | 判据 | 判定方式 |
|---|---|---|
| A1 | **可按 run 检索** | 用例：按 `run_id` 过滤（一次运行的全部 span） |
| A2 | 可按 thread 检索 | 用例：按 `thread_id` 过滤 |
| A3 | 可按时间检索 | 用例：时间窗过滤 |
| A4 | 可按节点名检索 | 用例：按节点名过滤 |
| A5 | 四类过滤**组合** | 组合用例（如 `run_id` + 节点名） |
| A6 | 两后端可替换 | 同一查询在 JSONL / SQLite 后端结果等价 |

### 7. 关键实体与契约

| 实体 | 语义 | 对应契约 |
|---|---|---|
| 查询请求 / 响应 | 过滤条件（`run_id` / `thread_id` / 时间 / 节点名）+ 结果集合（JSON 可序列化） | **✅ C27**（缺口 1 已关闭，2026-11-05 · D11；`run_id` 过滤器同日追加） |
| trace 记录 | span 的持久化形态 | 与 B20F1 一致 |

> ✅ **口径（已冻结 · D11 批准 2026-11-05 + 发起者追加 `run_id`）**：查询结构已随
> **C27** 冻结——
> ① **请求**：过滤条件 **`run_id`** / `thread_id` / 时间范围 / 节点名（**四者可组合**）；
> ② **响应**：结果集合，**MUST JSON 可序列化**（纯数据，不含不可序列化对象）；
> ③ 存储与查询 MUST 经由**同一协议**、后端可替换（JSONL / SQLite 等价）；
> ④ 表结构与文件格式 MUST 视为**内部实现细节**（对外只暴露查询 API）。
> → **本 feature 的义务**：按 C27 逐字段实现，并把结构写入 spec。

### 8. 边界（本 feature 明确不做）

- 不实现 OTLP 导出（属 B21F1）。
- 不实现前端 / UI（v2 / B26）——但**查询 API 必须已为 UI 预留**（§5.8.3 的缺口 1
  即为此而设）。
- 不实现本地 Agent Server（v2 / D8）。
- 不实现 Postgres 后端（v2 范围，未排 feature）。
- 不实现 trace 的保留期 / 清理策略（v1 不做）。
- 不实现评测 / 数据集（永不做）。

### 9. 红线与质量门禁

- **依赖门禁（阻断，红线）**：零第三方依赖（`sqlite3` 属标准库）。
- **零出站 / 零环境变量**。
- **可视化不阻断执行**（宪法原则 IV）：查询失败 MUST NOT 影响运行。
- **ARCH-1 / ARCH-3**：L5 只依赖 L1；跨层只传纯数据。
- **人工门禁**：`harness/verification/<feature>/manual-verification.md`。
- **证据门禁**：查询语义与可替换性须有可判定用例。

### 10. 交付物与后续

- **交付物**：Trace 查询 API（三类过滤 + 组合 + 稳定排序）、SQLite 后端、
  后端可替换性适配、单元测试 + 人工验证记录。
- **后续解锁**：**B21F1**（OTLP 导出插件 + 后端对接文档）→ **B14F1**（持久化层）。
- **风险提示**：SQLite 在 **Windows 上的文件锁差异**（立项书 §3.5）——并发写用例
  MUST 在 Windows CI 上跑。spec 阶段应把「并发写入 + 查询」列为一条跨平台验收项。
