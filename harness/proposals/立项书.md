## 摘要

**一句话**：freegraph 是一个**零第三方运行时依赖、零出站（自身不主动出网）、零账号**的图运行内核（Graph Runtime），以与 LangGraph Graph API **同名同签名**的接口提供 `state schema / node / edge` 三项基础能力，并自带本地可诊断能力。

| 关键项 | 结果 |
|---|---|
| 项目定位 | 官方术语中的 **Runtime 层**（对标 LangGraph）；Framework 层由后续独立项目 freechain 承担，Harness 层不做 [17] |
| 交付物 | `freegraph` Python 包 v1.0（**发行名 = 导入名 = `freegraph`**；契约层为**主包内子模块**，不拆独立发行包 —— **D1 已拍板**，见 §12）：**24 个 功能块 / 32 个 feature / 33,005 行**（实现 16,271 + 测试 16,734）。**B17（Store）已砍**（2026-11-05 决议，见 §12 D5）——理由：Store 是**跨会话 / 跨图**能力，而 **图 = 一个进程**，超出「单进程图框架」的定位，复杂且违背初衷；契约 **C20 仍冻结**（实现后补，v2） |

## 1. 项目概述

### 1.1 定位

| 层 | 官方产品 | 本项目对应 |
|---|---|---|
| Runtime | LangGraph | ✅ **freegraph 对标此层** |
| Framework | LangChain | ✅ freechain（后续独立项目，基于 freegraph 构建） |
| Harness | Deep Agents | ❌ 不做 |

### 1.2 两条项目路线

| 项目 | 交付 | 依赖 |
|---|---|---|
| **freegraph**（本仓库） | 图运行内核：状态模型 / 节点 / 边与路由 / 运行时 / 可观测 | 零 LangChain、零 LangSmith 依赖 |
| **freechain**（后续项目） | 替代 LangChain 的上层：模型抽象、工具、消息、agent 装配 | 基于 freegraph 构建 |

**定位补充（2026-11-05 决议）**：freegraph 的初衷是做成一个**通用图框架**——目标场景除
**智能体开发**外，还包括 **RPA 自动化**、**脚本编排**（一定程度上**替代 `main` 函数**）、
**可视化工作流编排**。由此确立一条**范围边界（决定性）**：这类场景的共同前提是
「**图 = 一个进程**」→ **跨会话 / 跨图**能力（如长期记忆 `Store`）**不属于 v1**（见 §12 D5）。
该边界是**定位推导出的硬边界**，不是「先不做再说」的临时取舍；**不改变**两条验收目标
（G1 / G2）。

**项目性质（2026-11-05 补充）**：本项目是**个人开源项目**——其定位同时是**作品集 / 名片 /
能力证明**（个人项目在求职与商务合作中的展示物），**非以盈利为直接目的**。
这一性质**直接决定了许可证选择（§12 D3）**：MIT 的**单向兼容性**使 freegraph 的代码
可被嵌入**任意**许可族的下游项目 → 最大化「有人用我的代码」的采纳面；
**Apache-2.0 的额外条款（专利 / 商标 / 贡献者再授权 / NOTICE / §9）对本项目均属空条款**，
却把许可证从 1 页变成 11 页。同理，它也意味着**仓库本身（宪法 / 调研报告 / 验收脚本 /
32 份 feature 规格）就是作品集的主体**——「可审计的契约」与「充分的人工验证」既是质量底线，
也是能力证明。

### 2.3 三条差异化承诺

| 承诺 | 官方现状 | freegraph v1 |
|---|---|---|
| **零账号** | 免费档强制 LangSmith 账号 + API key [4][8] | 无账号、无 key 可完成全流程 |
| **零出站** | PNG 渲染走公网、tracing 上报、license 校验出网 [4][6] | **freegraph 自身零出站**；可选 OTLP exporter 仅在用户显式传入时生效；**不限制、不阻断用户代码的出网**（节点访问外网、模型调用、工具调第三方 API 一律照常） |
| **零 license key** | standalone server 仍需 license key + beacon 出网 [16] | 不需要 |

> 三项承诺互相独立：零账号不蕴含零出站（PNG 渲染不需要任何账号却必外呼），零出站不蕴含零 license key。
> **「零出站」的约束对象是 freegraph 自己**：它是一条**对框架行为的约束**，**不是对宿主程序的限制**——freegraph 不安装、不启用任何出网拦截机制，用户代码想连哪里连哪里。

## 4. 项目目标与范围

### 4.1 总目标

在复刻 LangGraph Graph API 三项基础能力（官方术语：**state schema / node / edge**，另含 `Command` / `interrupt` 等）的前提下，提供彻底剥离 LangSmith、且内核不依赖 LangChain 的图运行与可观测能力。

> **类别口径（三类，合计 18 = 7 + 1 + 10，可复算）**：
> - **同名同签名（7 项：#1–#7）** —— 方法名与签名不得改，否则脚本原样跑不起来；

| 领域 | `A1`–`A8` | 8 | 固定（交付分组） | 追加 A9 |
| **功能块** | `B1`–`B25`（+`B26` v2 预备） | 25(+1) | **全局整数，按领域连续分配** | **追加 B27，既有编号不变** |
| **feature** | `B<n>F<m>` | 32 | **在所属 功能块 内从 1 编号**（按该 功能块 内的执行顺序） | **在所属 功能块 末尾追加 F<m+1>，既有编号不变** |
| 事实 / 指标 / 风险 / 决策 / 契约 | `E` / `S` / `R` / `D` / `C` | —— | 各文档内自洽 | 追加 |

> **为什么不用全局递增的 feature 编号**：全局编号（如 P01…P32）在中途插入功能时必须重排全部后续编号 —— 改动面大、追溯断裂、且会让已合并的分支与文档失配。**功能块 内编号把重排风险降到零**：新增能力只是在所属 功能块 末尾追加一个 `F<m+1>`，其余编号与依赖关系完全不动。
>
> **因此 §5.2 总表的「行序 = 执行顺序」，而「feature ID = 稳定标识符」**：两者解耦，表内 ID 看上去不连续是正常的。

## 5. 技术方案

### 5.1 架构（拍板）：6 层单向依赖 + 1 个契约层

**三个单元的定义**

| 单元 | 是什么 | 决定什么 | 谁来读 |
|---|---|---|---|
| **层（Layer）** | 代码组织：**谁 import 谁** | 架构与 CI import 图断言（ARCH-1/3） | 架构评审、CI |
| **功能块** | 交付单元：一个可独立验收的能力切片 | 需求与验收的勾选粒度 | 需求评审、验收 |
| **feature** | 执行单元：一次 speckit 闭环（specify→plan→tasks→implement） | 排期与成本 | 计划与排期 |

> **层 ≠ 功能块 ≠ feature**：一个 功能块 通常落在一层内（例：A5 全部在 L4），但可跨层（A3 的 `compile()` 在 L3、调度在 L2）；一个 功能块 可含多个 feature（B7 含 3 个）。**因此不可用其中一维去描述另一维**——§5.2 的总表是三者唯一的合并视图。

**层号 = 依赖层级 = 开发顺序（低层先、高层后）**

| 事实 | 证据 |
|---|---|
| 图定义层 **import** 运行时层 | `langgraph/graph/state.py:73-75` → `from langgraph.pregel import Pregel` / `pregel._read` / `pregel._write` [3] |
| 运行时层**不** import 图定义层 | `langgraph/pregel/main.py` 无任何 `langgraph.graph` 引用 [3] |
| 编译产物即运行时实例 | `CompiledStateGraph` 的基类链为 `CompiledGraph(Pregel)` [3] |

> **结论（拍板）**：运行时层是**独立性最高**的一层（不依赖任何上层），因此**先开发运行时层、再开发图定义层**。§5.2 总表的 feature 序即按此排布（**行序以 §5.2 总表为准**，不另设全局编号）：L1 契约 → **L2 运行时** → L3 图定义 → L4 持久化 / L5 可观测 → 交付。
>
> **由此获得的三个工程收益**：
> 1. **运行时可脱离构建器独立验收** —— 调度循环（B7F1）不再依赖 `compile()`，可用手写图规格直接测试（对应 LangGraph 中 Pregel 可被直接实例化）；
> 2. **最高风险前置** —— C4 稀疏状态、C8 fresh 读、super-step 并发写等**静默破坏**型语义在早期暴露，而不是等到构建器完成后才发现；
> 3. **构建器层更薄** —— `StateGraph` 只是「schema → channel 规格 + 节点规格 + 边 → 路由」的适配器，风险集中在已验收的运行时之上。
>
> **代价（须记录）**：固定脚本的最小交付集 = **B6F1（构建器）+ B7F2（compile）+ B7F3（invoke）+ B8F1（条件边路由）+ B22F1（`get_graph`）+ B23F1（`draw_mermaid_png`）** 共 **6 项**——其中 **B22F1 / B23F1 必须先于 `invoke()` 就绪**，因为 `target.py:144` 的 `agent.get_graph(xray=True).draw_mermaid_png()` 位于第 149 行 `agent.invoke(...)` **之前**（Q3 §3.5 风险 1 已实测：离线必抛 `ValueError: Failed to reach https://mermaid.ink API`，脚本会在到达验收点前中断）；漏掉这两项或漏掉 B6F1/B7F2（没有图可编译），脚本都无法跑通。
> 完成时点有**两个口径，必须同时看**：**依赖链口径（理想并行）第 30 天**（受 B7F3 的 10-feature 长链约束）；**§5.2 行序串行口径 = 第 14–20 个 feature / 第 60 天**（报价按此口径）。M2 在串行序列中位于**第 14–21 个 feature**（M2 整体于第 63 天结束），全项目 96 天不变、关键路径 **15 个 feature（45 天）**。

**依赖方向铁律**

1. 只能向下依赖；反向 import 一律禁止；
2. L1 不 import 任何内部层（**仅标准库**）；
3. L2–L5 之间不横向依赖（如持久化层不得 import 可观测层），关联只经由 L1 的协议；
4. L6 是唯一可横向依赖 L5 的层，且只读 Contract 数据（JSON / dict），不反向写内核。

| 约束 | 判定方式 |
|---|---|
| ARCH-1 依赖方向单向；L1 不依赖任何内部层 | CI AST 扫描 import 图：**L1→L6 编号递增方向即允许方向**（高层可 import 低层），**反向 import 视为违规**；跨层单元（层 = 「—」）只能 import L1 与更低层，不得被 L2–L5 import<br>**【例外 · 2026-11-07 发起者裁定】公开 API 门面 `freegraph/graph.py`（层 =「—」，B2F2）是唯一例外**：它按定义**横跨 L1–L3**（`Command` / `RunConfig` 属 L1 契约层、`Send` / `interrupt` 属 L2 执行内核层、`StateGraph` 属 L3 图定义层），故**允许 import L1–L3**（仍**不得** import L4 持久化 / L5 可观测）。其余跨层单元（工程设施 / 发行与文档）维持「只能 import L1 与更低层」 |
| ARCH-2 契约层可独立安装，**零**第三方依赖 | 单独 import 无副作用；**且 `freegraph/__init__.py` MUST 保持惰性 / 空壳**——`import freegraph` 后 `sys.modules` 中 MUST NOT 出现 `freegraph.graph` / `freegraph.runtime` / `freegraph.persistence` / `freegraph.observability`（**D1 决议的附加约束**：否则契约层「可独立消费」的收益失效，freechain 无法只取契约） |
| ARCH-3 跨层只经由 `Protocol` + 纯数据类 | CI 静态检查 |
| ARCH-4 公开 API 面只经由 L1 导出 | API 快照测试 |

#### §5.3.1 C22 / C23 的字段级约定（2026-11-05 · D11 批准 · 同步自 Q8 §3.4.1）

| 契约 | 约定 | 理由 |

| **C22**（标识职责划分） | `thread_id` = **会话**标识，由 `RunConfig` 承载（**字段清单不变**：`thread_id` / `context` / `metadata` / `tags`）；`run_id` = **单次运行**标识，由 freegraph 在每次 `invoke` / `stream` 开始时生成，**MUST NOT 可由用户指定或覆盖**（故**不进** `RunConfig` 字段清单——它是运行期产物而非配置项）；`metadata` / `tags` 为附加信息，不参与标识 | 缺口 3：两条事件通道（`stream()` 与 `TraceSink`）此前无共享标识 → 无法把「一次运行的事件流」与「一次运行的 span 树」对齐 |

> #### §5.3.1 ④ C17 的修订（2026-11-05 · 发起者决策）：**中断恢复 MUST 挂 checkpointer**
>
> | 修订内容 | 理由（发起者原话要点） |
> |---|---|
> | **恢复 MUST 挂 checkpointer**：图被 `interrupt()` 挂起后，用 `Command(resume=...)` 恢复**必须**经由 checkpointer 读取被中断处的状态（快照 + pending writes）并**从节点起点重跑**。**MUST NOT** 提供「不挂 checkpointer 也能恢复」的内存态旁路；未挂 checkpointer 时调用恢复**必须**抛明确异常。 | ① **内存态恢复不可靠**：LangGraph 的 MemorySaver 仅限**开发 / 调试**，不可用于生产；而 `interrupt` 的主要场景是 **time travel**——可能隔了很长时间、甚至**电脑重启之后**，图状态仍须可恢复。② **SQLite 是智能体开发的事实标准**：智能体是低并发应用，用户需要**开箱即用**（不配置额外中间件 / 数据库），故各大智能体都采用 SQLite；面对 SQLite 就**必须**像 LangGraph 那样采用 checkpointer。③ 「用户第一次用 HITL 就得先建 saver」**不是负担，而是选择持久化中间件的过程，不能省略**。 |
>
> **落地 feature**：B10F1（恢复入口校验）+ B14F1（`MemorySaver`，开发 / 调试定位）+
> **B15F1**（`SqliteSaver`，开箱即用的事实标准）+ B16F1（time travel 组合能力）。
>
> **落地 feature**：C22 / C23 字段约定 → **B18F1**（span 必带字段）+ **B19F1**（`TraceSink` 接入）
> + **B8F2**（`stream()` 事件带 `run_id` / `thread_id`）；C27 → **B20F1** + **B20F2**。
>
> **`run_id` 的语义（2026-11-05 追加）**：把图中**每个节点视作一个微服务**，则 `run_id` 是
> **链路监控的唯一通行证**——等价于分布式追踪的 **trace id**。三条不变式：
> ① **运行时生成、用户不可设置**（MUST NOT 可由用户指定或覆盖；用户自带标识需求用
> `thread_id` / `metadata` / `tags`）；② **一次运行一个 `run_id`**（该次运行的所有节点、
> 工具、模型调用与事件共享它）；③ **可查**（是 C27 查询 API 的过滤器之一，使「精确回查
> 某一次运行」成为可能）。
> **为什么不进 `RunConfig`**：该类型的字段清单已在 B1F1 冻结；且 `run_id` 按不变式 ①
> **本就不可配置**，放进配置载体反而暗示「可配置」。

> **口径说明（易混项）**：**C21 = `context` 独立通道**，**C22 = `RunConfig`**（`thread_id` / `context` / `metadata` / `tags`）。二者职责不同：前者是**状态/运行时上下文**的传递通道，后者是**每次运行的配置**载体。二者在本表之外的引用（§5.2 B8F3、§5.8.1、§5.8.3）均按此口径。

> **v1 口径（D14 修订后 · **2026-11-08 宪法 v1.7.0 修订**）**：**v1.0 零依赖** ⇒ v1.0 的发行元数据**不含 `[png]`** ⇒ B23F1 在 **v1.0 只交付占位 PNG**（C 方案：可被 `IPython.display.Image` 接受的合法 PNG 字节，**离线不得抛异常**、**不得外呼**，§9.2 约束 6）⇒ **真 PNG 渲染（D 方案）随 `[png]` extra 归 v2.0**，且**渲染后端方向（`playwright` / 自研最小渲染器 / 继续只出占位 PNG）留待 v2.0 专项调研后决策**（发起者 2026-11-08 决议）—— **v1.0 的两段式退化为「只有占位 PNG 一段」**。
> **📌 三候选与代价（v2.0 专项调研的输入）**：① **`playwright`**（白名单下**唯一实测可行** · Apache-2.0）—— 图形保真度高，但用户需**显式** `playwright install chromium`（**约 300 MB** · 安装期动作 · 运行期零出站）；② **自研最小 SVG→PNG 渲染器**（纯标准库 `zlib` + `struct`）—— **永久零依赖**，但工作量与图形保真度需评估；③ **继续只出占位 PNG** —— 零依赖零工作量，但无「真图」能力。
> **为何 v1 就交付真实渲染（原「真实渲染列入 v2」的判断经复核不成立）**：白名单严格口径（宪法原则 IX · {MIT, Apache-2.0, BSD-2/3, PSF-2.0}）下，**全部纯 Python SVG→PNG 后端实测被拒** —— `cairosvg` / `svglib` / `pycairo` = **LGPL**（传染性）· `pillow` = `MIT-CMU` / `HPND`（变体标识符不放行）· `matplotlib` 的闭包含 `pillow` 且 `numpy` 的表达式含 `0BSD` / `Zlib` / `CC0-1.0` · `pymupdf` = **AGPL** · `resvg-py` = **无任何许可证信息** ⇒ **`playwright` 是唯一闭包全绿的后端**（实测：Apache-2.0，闭包 `greenlet` / `pyee` / `typing-extensions` 皆白名单）。
> **代价（须记录）**：`[png]` 用户需另装浏览器二进制（约 300 MB · 安装期下载）⇒ **基础安装的零依赖承诺不受影响**（extra 默认关闭）。
> **v2 保留**：纯 Python 最小渲染器（B26 可选子包）—— 目标是**摆脱浏览器依赖**，不是替换 v1 的默认行为。

### 5.9 执行路线：上游优先 · 差分证据 · 破冻结面登记（2026-11-12 决议 · 宪法 v1.9.0）

> **背景**：本项目的产品本质是「**零账号 / 零主动出站 / 零依赖**的 langgraph 替代品」⇒
> 它的正确性**不来自「更好的设计」，而来自「与上游同款」**⇒ 但 speckit 流程曾让
> 「智能体 + 大模型自由发挥」⇒ feature 之间越来越无法对齐 ⇒ **需要人工决策的地方越来越多**
> （发起者原话：「我疲于奔命，狂做选择题」）⇒ **实测证据**：P3 回改轮里 **B4F1 的
> 「只接受 `TypedDict`」**、**B5F2 的「fresh 视图保留路由通道」**、**B9F1 的
> 「空列表 = 无操作」** 三处分叉**长期保持绿色** —— 因为既有的 8 个验收脚本只验
> 「freegraph 符合自己的 spec」，**证不了「与上游同款」**。
> ⇒ 本节把「**怎么执行**」写成条款（权威：**宪法 v1.9.0 原则 XI**）。

| # | 条款 | 内容 | 判据 / 落点 |
|---|---|---|---|
| **E-1** | **上游是唯一权威** | 每个设计点 MUST 按「① 上游有 ⇒ **照抄**（含缺陷与怪癖）② 上游无 ⇒ 落自研区 ③ 自研区的点 MUST 登记并论证」裁决，**不得跳步** | 每个 feature 的 spec MUST 含「**上游对照**」小节（模板已内置 · `.specify/templates/spec-template.md`） |
| **E-2** | **必须自研区（只有 4 类）** | ① 零账号 / 零主动出站 / 零依赖的硬约束 ② 上游自身的缺陷或不确定 ③ 上游没有的能力 ④ 下游 langchain 兼容适配层 ⇒ **不属此四类的分叉一律照抄** | 自研区的点 MUST 在「上游对照」表里写明「上游无此项 + 理由 + 判据」 |
| **E-3** | **行为面照抄 · 失败信号可更严** | 成功路径的可观察状态 MUST 照抄；失败信号 MAY 更严，但 MUST **标注「比上游更严」并写明理由** ⇒ **MUST NOT** 用「更严」掩盖行为面的偏离 | 「上游对照」表的**关系列**只允许 `SAME` / `STRICTER` / `DIFF` 三态 |

### 6.2.1 发布节点（版本号节奏）

> **已由发起者拍板（2026-11-05）**，记为 §12 **D13**。v1 期间**只发两版**——
> 中间**不**发任何预发布版。

| 版本 | 触发条件 | 产物状态 | 定位 |
|---|---|---|---|
| `0.0.x` | **已发**（v0.0.1 / v0.0.2 / v0.0.3） | **占位版**：仅锁定发行名 + 验证发布链路，**不含任何内核功能**；v0.0.3 起零第三方依赖、最低 Python 3.11 | 名字占位 |
| **`0.1.0`** | **全部 32 个 feature 开发完成**（M4 末 · B25F1 之后） | **功能完整**：契约层 + 运行时内核 + 图定义 + 可观测 + 持久化 + OTLP + 兼容矩阵 + 双跑验收（fake CI + 真实模型人工）各一轮 | **「能跑」的版本** —— 但**未经充分调试与内测** |
| **`v1.0.0`** | `0.1.0` 之后经历**充分调试、内测、健壮性加固** | 稳定性达标后的正式版 | **正式版**（立项书 §5 的 v1.0 口径） |

**为什么不在中间发版**（三条硬约束）：

1. **PyPI 版本不可删除，只能 yank** —— 每发一版就是一条**永久**记录。
   32 个 feature 各发一版 = 32 条永久的内部里程碑记录，对用户零价值。
2. **`0.0.x` 的定位是「占位版」** —— README 与 `freegraph/__init__.py` 均写明
   「只为在 PyPI 上锁定发行名，内核功能尚未实现」。功能落地后要**一次性**离开 `0.0.x`，
   而不是渐进式爬 `0.0.4 → 0.0.9`（否则用户会以为 `0.0.9` 仍是占位版）。
3. **契约层是冻结面** —— 一旦发布，改字段名 / 字段注解即破坏性变更。
   在契约层与运行时都还在动的阶段发布，等于把未定的 API 钉死。

**代价（明确记录）**：`0.1.0` 之前，PyPI 上的 freegraph 始终是「只有版本号」的占位版；
姊妹项目 **freechain** 若需基于 freegraph 开发，须等 `0.1.0`（或本地 `pip install -e .`）。

**发 `0.1.0` 那天的动作清单**（可逐条核对）：

| 2 | **README 的「占位版」措辞**改为「v0.1.0 起为首个功能版本」 |
| 3 | **`freegraph/__init__.py` docstring 的「占位版」段落**同步改写 |

**基准**：固定脚本（151 行，只读，源自 LangGraph Quickstart "Full code example" 的机械替换版）[1][2]。

**验收脚本集（`harness/demo/`，四组 + 编排器）**

固定脚本验证的是**生态兼容性**（freegraph 与 LangChain 的模型 / 工具对象能否共处）；

后两者必须分开——内核未开工时 CI 应显示「环境未就绪」而非「验收失败」。

**脚本里的检查分两类**：**硬断言**（章程已锁定形态，失败即 FAIL）与**软断言**
（语义由章程规定、但调用形态尚未拍板，不判失败、只标注「待锁定」，形态拍板后升级为硬断言）。
当前软断言三处：C25 节点别名的调用形态（B8F3 拍板）、`recursion_limit` 的载体（B13F1）、
`interrupt` 恢复是否依赖 checkpointer（B14F1）。

**已拍板（2026-11-05）**：`interrupt` 恢复**必须依赖 checkpointer**（内存态恢复不可靠；
`interrupt` 的主场景是 time travel，须跨长时间 / 跨重启可恢复；SQLite 是智能体开发的事实
标准，必须像 LangGraph 那样采用 checkpointer）→ 该软断言**形态已锁定**，待 **B14F1**
落地时随真实 `MemorySaver` 一并**升级为硬断言**（`harness/demo/graph_core.py`）。

**M3 的可诊断性脚本（trace / 检查点 / 时间旅行）暂缺**：其依赖的四个 API 形态章程尚未锁定
（`compile(tracer=)` 的载体、本地 trace 目录参数名、`MemorySaver` 的模块路径、
`update_state(...)` 的签名），**随 M3（B14F1–B20F2）的各 feature 一并补齐**——
验收脚本应与它所验收的能力的 API 形态同时确定，避免在形态未知时先行猜测。
脚本集的接口形态说明见 `harness/demo/README.md`。

**依赖红线的作用域：两个环境，两套断言**

> **问题**：`target.py` 自带 `from langchain.tools import tool` / `chat_models` / `messages`（第 3–4、54、64、87、147 行）。验收环境**必然**安装 `langchain` → `langchain-core` → `langsmith`（硬依赖，非 extras，见 E7）[2][5]。
> 若把 S1 判成「环境全量依赖树无 `langsmith`」，则**验收环境自身即违规**，门禁无法实现——这是口径问题，不是红线问题。
> **红线约束的对象是 freegraph 自己**：它的依赖声明、它的 import、它的网络行为。它**不**约束用户脚本装了什么。

| 环境 | 装什么 | 用途 | 断言 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| **① 依赖断言环境**（隔离 venv） | **只装 `freegraph` 基础包**（**零**必装依赖） | 断言 freegraph 的依赖闭包与 import 副作用 | ① 递归展开 freegraph 自身 `Requires-Dist`（含全部 extras 变体）无 `langsmith` / `langchain*` / `langgraph*`；② `import freegraph` 后 `sys.modules` 中无 `langsmith` / `langchain_core` / `langgraph` |

**「框架零出站」的验证方法（只观测，不阻断）**

> **设计立场**：freegraph 是**函数胶水 / 工作流框架**。它承诺的是「**自己不会偷偷联网**」，**不是**「你的程序不许联网」。
> 因此 freegraph **不安装、不启用任何出网拦截机制**：节点函数访问外网、调用真实模型、工具访问第三方 API，**一律照常工作**——框架不改变宿主程序的语义。

| # | 环节 | 做法 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 1 | **不阻断** | 夹具只包装 `socket.connect` / `socket.create_connection` 以**记录**目标与调用栈，**放行**所有连接；**不抛异常、不拒绝连接** |
| 2 | **按发起方归因** | 调用栈中出现 `freegraph/` 包路径 → 判为「**框架出站**」；否则判为「**用户出站**」（模型调用、节点自建 HTTP 客户端等） |
| 3 | **断言** | **框架出站数 = 0**；用户出站**记录在案但不判失败**。唯一例外：用户显式启用并传入端点的 OTLP exporter（§5.5 网络层白名单） |
| 4 | **静态佐证** | CI 静态扫描 `freegraph/**`（排除可选 OTLP exporter 模块）不得出现 `socket` / `requests` / `httpx` / `urllib.request` 等网络客户端调用 |
| 5 | **断网等价性** | 另跑一轮「全部网络接口置为不可用」的 CI 任务，确认 freegraph 自身功能完整可用（宪法原则 I） |

> **与宪法的一致性**：宪法原则 V 的 Requirement「**MUST** 有『零出站』的可判定证据」不变；其门禁 4 的方法性措辞原文为「socket guard 夹具（**拦截**所有非 localhost 的 `socket.connect`，断言拦截列表为空）」。
> 本节的实现口径为「**只观测不阻断 + 按发起方归因**」，**须同步走宪法 PATCH 修订**（修订对象：原则 V 门禁 4 与原则 V 的方法性措辞；修订理由见 §10 的 R11）。原则 I「零出站」的实质要求——**freegraph 自身零出站、断网可用**——完全保留。

**验收执行**

| 轮次 | 模型 | 环境 | 证据 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| ⓪ 依赖断言轮 | 不需要模型 | **隔离 venv**：只装 `freegraph` 基础包 | S1①②：依赖闭包无 `langsmith` / `langchain*` / `langgraph*`；`import freegraph` 后 `sys.modules` 无 `langsmith` / `langchain_core` |
| ① CI 轮 | fake / 伪模型（**经 `conftest.py` 猴补 `init_chat_model` 注入，固定输出序列见上**） | **验收环境**：清空全部 `LANGSMITH_*` + **socket 监测夹具（只观测、不阻断、按调用栈归因）** | CI 日志 + **「框架出站」计数 = 0**（用户出站记录在案，不判失败）+ **反向断言**：freegraph 运行期未 import `langchain`（S1③）+ **fake 断言点**（`llm_calls == 2`、工具结果 = 7、`messages` 长度 = 3） |
